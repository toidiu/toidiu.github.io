Crypto and security review cheatsheet

Quick-reference notes for a crypto and security review interview: primitives, attacks, and how to review architectures and code for vulnerabilities.

Primitives

Hash

  • Purpose and guarantee
    • Unkeyed fingerprint: for an n-bit hash, preimage and second preimage cost about 2^n, collision about 2^(n/2) (SP 800-107 Rev 1 section 4; section number uncertain).
    • Collision resistance fails first (birthday bound), and it is what SHA-1 lost (gap Q1).
    • On Merkle-Damgard hashes, a second preimage for a 2^k-block message costs about 2^n / 2^k (Kelsey and Schneier, EUROCRYPT 2005).
    • Not authenticity: no key, so anyone recomputes the digest of a modified message (our reasoning).
    • Not hiding of low-entropy input: SHA-256(phone number) falls to enumeration (our reasoning).
    • Not a MAC: SHA-256 and SHA-512 output the full internal state, so H(secret || m) allows length extension (see Attacks > Hash length extension).
  • Why collisions break signatures (gap Q1)
    • The attacker builds a benign and an evil document with one hash and gets the benign one signed; the signature verifies on the evil one (Stevens et al., CRYPTO 2017).
    • Real case: Flame forged a Microsoft code-signing certificate with an MD5 chosen-prefix collision, 2012 (Stevens, CRYPTO 2013).
    • HMAC-SHA-1 still holds: HMAC needs the compression function to be a PRF, not collision resistance (Bellare, CRYPTO 2006).
      • Without the key the attacker cannot search for HMAC collisions offline (Bellare 2006).
  • Picks and avoid
    • Pick SHA-256, SHA-384, SHA-512/256 (FIPS 180-4), SHA3-256 (FIPS 202) or BLAKE2 (RFC 7693).
    • Avoid MD5: practical collisions (RFC 6151).
    • Avoid SHA-1: SHAttered identical-prefix collision 2017, Shambles chosen-prefix 2020; preimage resistance still holds (Leurent and Peyrin, USENIX Security 2020).
      • SP 800-131A Rev 2 disallows SHA-1 for signature generation.
  • OpenSSL APIs
    • One-shot EVP_Digest(m, n, md, &mdlen, EVP_sha256(), NULL); streaming EVP_DigestInit_ex2, EVP_DigestUpdate, EVP_DigestFinal_ex (OpenSSL EVP_DigestInit(3)).
    • Fetch by name: "SHA2-256", "SHA3-256", "BLAKE2B-512" (OpenSSL EVP_MD-SHA2(7), EVP_MD-SHA3(7), EVP_MD-BLAKE2(7)).
  • Misuse to spot
    • Secret-prefix hash as a MAC, MD5 or SHA-1 in signature or certificate paths, or a hash of a guessable value called "anonymized" (our reasoning).
/* Finding: secret-prefix MAC; length extension forges tags. */
void tag(const uint8_t *k, size_t kl, const uint8_t *m, size_t ml,
         uint8_t out[32]) {
    EVP_MD_CTX *c = EVP_MD_CTX_new();
    EVP_DigestInit_ex2(c, EVP_sha256(), NULL);
    EVP_DigestUpdate(c, k, kl);
    EVP_DigestUpdate(c, m, ml);
    EVP_DigestFinal_ex(c, out, NULL);
    EVP_MD_CTX_free(c);
}

MAC

  • Purpose and guarantee
    • Integrity and origin authentication between key holders: without the key, no valid tag on a new message (RFC 2104; FIPS 198-1).
    • Not non-repudiation: every verifier holds the key and can forge (FIPS 186-5 section 1 gives that property to signatures only).
    • Not freshness: a replayed message and tag still verify (see Attacks > Replay); not confidentiality.
  • MAC or signature (gap Q2, closed)
    • MAC when the verifier is the signer or in its trust domain: a service checking its own cookies, internal request signing (our reasoning).
    • Signature when verifiers must not be able to mint tags: public tokens, software updates, certificates (FIPS 186-5 section 1).
  • Picks and avoid
    • Pick HMAC-SHA-256 (RFC 2104, FIPS 198-1), KMAC256 (SP 800-185), CMAC-AES (SP 800-38B) or keyed BLAKE2 (RFC 7693).
    • Poly1305 and GMAC break if a key or nonce repeats; use them only inside an AEAD (RFC 8439 section 2.5; SP 800-38D).
    • Tag length: RFC 2104 section 5 sets a floor of half the hash output and at least 80 bits; we default to the full tag.
    • Avoid H(key || m): length extension on MD5, SHA-1, SHA-256, SHA-512 (see Attacks > Hash length extension).
    • Avoid raw CBC-MAC on variable-length messages: proven only for fixed length (Bellare, Kilian, Rogaway, CRYPTO 1994); CMAC fixes it (SP 800-38B).
  • OpenSSL APIs
    • One-shot HMAC(EVP_sha256(), key, klen, m, n, tag, &len) (OpenSSL HMAC(3)).
    • Generic EVP_Q_mac(NULL, "HMAC", NULL, "SHA256", NULL, key, klen, m, n, tag, sizeof tag, &len) (OpenSSL EVP_MAC(3), EVP_MAC-HMAC(7)).
    • Compare tags with CRYPTO_memcmp (OpenSSL CRYPTO_memcmp(3)); code in Attacks > Timing side channels.
  • Misuse to spot
    • memcmp or strcmp on a tag, or a MAC over different bytes than the ones parsed, such as re-serialized JSON (our reasoning).

KDF

  • Purpose and guarantee
    • From input keying material (IKM) with enough entropy, output is indistinguishable from uniform; each info gives an independent key (RFC 5869 sections 1, 3.2).
    • Not added entropy: a password stays guessable at HKDF speed; use a password hash (RFC 5869 section 4).
  • Why HKDF after ECDH (gap Q4)
    • A DH output is a group element (X25519: a field element below 2^255 - 19), not uniform bits (RFC 7748 section 5).
    • Ciphers and PRF proofs assume uniform keys, so the raw secret needs extraction (RFC 5869 section 3.3; Krawczyk, CRYPTO 2010).
    • Extract: PRK = HMAC(salt, IKM) gives a uniform pseudorandom key (RFC 5869 section 2.2).
    • Expand: T(i) = HMAC(PRK, T(i-1) || info || i), up to 255 * HashLen bytes (RFC 5869 section 2.3).
    • A good key is uniform, secret, long enough for the target strength, and used for one purpose (SP 800-57 Part 1 Rev 5 section 5.2; uncertain as a full list).
  • Salt (gap Q4)
    • Public and optional; defaults to HashLen zero bytes; a fixed or reused salt is fine, and it need not come from a CSPRNG (RFC 5869 sections 2.2, 3.1).
    • A random salt strengthens extraction and separates applications; salt 0 is fine when IKM is strong (RFC 5869 section 3.1).
    • Rule: salt independent of IKM and not attacker-chosen (RFC 5869 section 3.4).
  • TLS 1.3 key schedule (gap Q4)
    • Derive-Secret(S, label, msgs) = HKDF-Expand-Label(S, label, Transcript-Hash(msgs), Hash.length): an Expand (RFC 8446 section 7.1).
    • Label and transcript hash both go into Expand's info (RFC 8446 section 7.1).
    • Derive-Secret(prev, "derived", "") uses label "derived" and the hash of an empty transcript; its output salts the next Extract (RFC 8446 section 7.1).
    • The first Extract (Early Secret) uses salt 0 and the PSK, or zeros, as IKM (RFC 8446 section 7.1).
  • Picks and avoid
    • Pick HKDF-SHA-256 (RFC 5869); SP 800-56C Rev 2 two-step for DH secrets; SP 800-108 KBKDF to derive keys from a key.
    • Avoid a raw DH secret as a key, ad hoc SHA256(secret), one info for two purposes, and HKDF on passwords (RFC 5869 sections 3.2, 4).
  • OpenSSL APIs
    • EVP_KDF_fetch(NULL, "HKDF", NULL) with params digest, key, salt, info, mode (OpenSSL EVP_KDF-HKDF(7)).
    • TLS 1.3 labels: "TLS13-KDF" (OpenSSL EVP_KDF-TLS13_KDF(7)).
/* HKDF-SHA-256, no salt (RFC 5869 default): one key per label. */
int derive(const uint8_t *ikm, size_t ikm_len, const char *label,
           uint8_t out[32]) {
    EVP_KDF *kdf = EVP_KDF_fetch(NULL, "HKDF", NULL);
    EVP_KDF_CTX *kctx = EVP_KDF_CTX_new(kdf);
    OSSL_PARAM params[4], *p = params;
    int ok;

    EVP_KDF_free(kdf);
    *p++ = OSSL_PARAM_construct_utf8_string(OSSL_KDF_PARAM_DIGEST,
                                            "SHA256", 0);
    *p++ = OSSL_PARAM_construct_octet_string(OSSL_KDF_PARAM_KEY,
                                             (void *)ikm, ikm_len);
    *p++ = OSSL_PARAM_construct_octet_string(OSSL_KDF_PARAM_INFO,
                                             (void *)label, strlen(label));
    *p = OSSL_PARAM_construct_end();
    ok = EVP_KDF_derive(kctx, out, 32, params) == 1;
    EVP_KDF_CTX_free(kctx);
    return ok;
}
  • Misuse to spot
    • memcpy(aes_key, secret, 32) after EVP_PKEY_derive, or one derived key for both encryption and MAC (see Attacks > Key reuse across purposes).

Password hashing

  • Purpose and guarantee
    • Makes each offline guess against a stolen hash cost time and memory (RFC 9106 section 1).
    • Not protection for a password already on a guess list; it only slows each guess (our reasoning).
    • We store salt, parameters and hash; at login we recompute with them and compare. Nothing is decrypted (gap Q5; RFC 9106 section 3.1).
    • Why not SHA-256 or HKDF: fast, with no work factor, so GPUs test guesses cheaply (OWASP Password Storage Cheat Sheet).
  • Picks and avoid
    • Pick Argon2id (RFC 9106 section 4): t=1, p=4, m=2 GiB first option; t=3, p=4, m=64 MiB second; 128-bit salt, 256-bit tag.
    • t is passes over memory, p is lanes (parallelism), m is memory in KiB (RFC 9106 section 3.1).
    • OWASP minimums: Argon2id m=19 MiB, t=2, p=1; scrypt N=2^17, r=8, p=1 (OWASP Password Storage Cheat Sheet).
    • bcrypt cost 10 or more, input cut at 72 bytes; PBKDF2-HMAC-SHA-256 600,000 iterations only where FIPS requires it (OWASP cheat sheet).
    • Avoid any fast hash, unsalted or globally salted hashes, and HKDF (RFC 5869 section 4).
  • What each input stops (gap Q5)
    • Salt, random and unique per user: stops precomputed tables and testing one guess against all users at once (RFC 9106 section 3.1).
    • Memory cost: each guess needs m of RAM, which caps GPU and ASIC parallelism; iterations alone do not (OpenSSL EVP_KDF-ARGON2(7)).
    • Argon2id addresses memory data-independently in the first half pass (side-channel resistant), data-dependently after (OpenSSL EVP_KDF-ARGON2(7)).
    • Optional pepper: a server secret passed as secret, kept outside the database (OpenSSL EVP_KDF-ARGON2(7)).
  • OpenSSL APIs
    • EVP_KDF_fetch(NULL, "ARGON2ID", NULL) with pass, salt, iter, lanes, memcost; OpenSSL 3.2 or later (OpenSSL EVP_KDF-ARGON2(7)).
    • Salt from RAND_bytes(salt, 16) (OpenSSL RAND_bytes(3)).
    • We found no PHC string encoder in OpenSSL, so we store the parameters ourselves (uncertain).
/* Argon2id, RFC 9106 second option: t=3, p=4, m=64 MiB. */
int pw_hash(const char *pw, const uint8_t salt[16], uint8_t out[32]) {
    EVP_KDF *kdf = EVP_KDF_fetch(NULL, "ARGON2ID", NULL);
    EVP_KDF_CTX *kctx = EVP_KDF_CTX_new(kdf);
    uint32_t t = 3, lanes = 4, m_kib = 65536;
    OSSL_PARAM params[6], *p = params;
    int ok;

    EVP_KDF_free(kdf);
    *p++ = OSSL_PARAM_construct_octet_string(OSSL_KDF_PARAM_PASSWORD,
                                             (void *)pw, strlen(pw));
    *p++ = OSSL_PARAM_construct_octet_string(OSSL_KDF_PARAM_SALT,
                                             (void *)salt, 16);
    *p++ = OSSL_PARAM_construct_uint32(OSSL_KDF_PARAM_ITER, &t);
    *p++ = OSSL_PARAM_construct_uint32(OSSL_KDF_PARAM_ARGON2_LANES,
                                       &lanes);
    *p++ = OSSL_PARAM_construct_uint32(OSSL_KDF_PARAM_ARGON2_MEMCOST,
                                       &m_kib);
    *p = OSSL_PARAM_construct_end();
    ok = EVP_KDF_derive(kctx, out, 32, params) == 1;
    EVP_KDF_CTX_free(kctx);
    return ok;
}
  • Misuse to spot
    • SHA256(password), one salt for all users, memcmp on the hash, or parameters not stored with the hash, so they can never be raised (our reasoning).

Symmetric/AEAD

  • Purpose and guarantee
    • With a unique nonce per key: confidentiality of the plaintext, integrity of ciphertext and AD; any change fails decryption (RFC 5116 section 2).
    • Not length hiding, and no replay, reordering or truncation protection across messages (see Attacks > Truncation, reordering and dropped messages).
    • Not key commitment: one GCM or ChaCha20-Poly1305 ciphertext can decrypt under two keys (Len, Grubbs, Ristenpart, USENIX Security 2021).
    • Not nonce-reuse safe: reuse leaks P1 xor P2 and, for GCM, enables forgery (see Attacks > Nonce and IV reuse).
  • Picks (gap Q6)
    • AES-256-GCM: fast and constant time with AES-NI and PCLMULQDQ; FIPS approved (SP 800-38D).
    • ChaCha20-Poly1305 without AES hardware: add, rotate, xor only, so constant time in software (RFC 8439).
      • Software table-based AES leaks key bits through cache timing (Bernstein, "Cache-timing attacks on AES", 2005).
    • Both take 96-bit nonces, so random nonces cap at 2^32 messages per key (SP 800-38D section 8.3).
      • Collision chance for q random nonces is about q^2 / 2^97: 2^-33 at q = 2^32 (birthday bound; our arithmetic).
    • XChaCha20-Poly1305: 192-bit nonce, same 256-bit key; random nonces need no counter (draft-irtf-cfrg-xchacha, expired draft).
      • Not in OpenSSL: EVP_CIPHER-CHACHA(7) lists only ChaCha20 and ChaCha20-Poly1305.
    • AES-GCM-SIV: the tag is a PRF of nonce, AD and plaintext and doubles as the CTR IV, so nonce reuse leaks only equality (RFC 8452).
      • Cost: two passes, so no streaming encryption (RFC 8452); in OpenSSL 3.2 or later (OpenSSL EVP_CIPHER-AES(7)).
  • Associated data (gap Q7)
    • Put in the context the ciphertext must stay bound to: table, column, row or user id, key version (our reasoning from RFC 5116).
    • It stops cut-and-paste: user A's ciphertext copied into user B's row fails the tag check (our reasoning, no cited incident).
    • AD is authenticated, not encrypted, and not carried in the ciphertext: the decryptor rebuilds it (RFC 5116 sections 2.1, 2.2).
  • Avoid
    • ECB, CBC or CTR without a MAC, and MAC-then-encrypt (see Attacks > ECB and unauthenticated encryption).
    • 64-bit block ciphers (3DES, Blowfish): SWEET32 (Bhargavan and Leurent, CCS 2016).
    • Truncated GCM tags (SP 800-38D appendix C).
  • OpenSSL APIs
    • EVP_EncryptInit_ex2(ctx, EVP_aes_256_gcm(), key, iv, NULL); AD via EVP_EncryptUpdate(ctx, NULL, &len, ad, adlen) (OpenSSL EVP_EncryptInit(3)).
    • Read the tag after EVP_EncryptFinal_ex with EVP_CTRL_AEAD_GET_TAG (OpenSSL EVP_EncryptInit(3)).
    • Decrypt: set the tag with EVP_CTRL_AEAD_SET_TAG; EVP_DecryptFinal_ex returns 0 or less on tag failure (OpenSSL EVP_EncryptInit(3)).
/* AES-256-GCM open: release plaintext only if the tag verifies. */
int open_gcm(const uint8_t key[32], const uint8_t iv[12],
             const uint8_t *ad, int adlen, const uint8_t *c, int clen,
             uint8_t tag[16], uint8_t *p) {
    EVP_CIPHER_CTX *ctx = EVP_CIPHER_CTX_new();
    int len, ok = 0;

    if (ctx != NULL
        && EVP_DecryptInit_ex2(ctx, EVP_aes_256_gcm(), key, iv, NULL)
        && EVP_DecryptUpdate(ctx, NULL, &len, ad, adlen)
        && EVP_DecryptUpdate(ctx, p, &len, c, clen)
        && EVP_CIPHER_CTX_ctrl(ctx, EVP_CTRL_AEAD_SET_TAG, 16, tag)
        && EVP_DecryptFinal_ex(ctx, p + len, &len) > 0)
        ok = 1;
    EVP_CIPHER_CTX_free(ctx);
    if (!ok)
        OPENSSL_cleanse(p, clen); /* never hand out unverified bytes */
    return ok;
}
  • Misuse to spot
    • Plaintext from EVP_DecryptUpdate used before EVP_DecryptFinal_ex succeeds, or that return value ignored (OpenSSL EVP_EncryptInit(3)).

Asymmetric encryption and KEM

  • Purpose and guarantee
    • Encrypt to a public key so only the private key holder decrypts; a KEM outputs a fresh shared secret plus its encapsulation (RFC 9180 section 4).
    • RSA-OAEP and HPKE target IND-CCA2 confidentiality (RFC 8017 section 7.1; RFC 9180 section 9.1).
    • Not guaranteed: sender authentication, since anyone with the public key can encrypt (HPKE base mode, RFC 9180 section 5.1.1).
      • HPKE Auth or PSK mode, or a signature, adds it.
  • Picks
    • Hybrid by default: a KEM wraps a fresh key, a KDF derives an AEAD key, the AEAD encrypts the data (RFC 9180 section 1).
      • Standard form: HPKE (RFC 9180 section 1), e.g. DHKEM(X25519, HKDF-SHA256) with AES-128-GCM or ChaCha20-Poly1305.
    • RSA-OAEP with SHA-256 and 3072-bit keys only when RSA is forced; 3072-bit RSA gives 128-bit security (SP 800-57 Part 1 Rev 5 table 2).
      • It fits k - 2*hLen - 2 bytes per operation: 190 bytes for RSA-2048 with SHA-256 (RFC 8017 section 7.1.1).
    • Large files: chunk with a streaming AEAD whose nonce holds a chunk counter and a last-chunk flag (STREAM, Hoang et al., CRYPTO 2015).
      • That detects truncation and reordering; age encrypts 64 KiB ChaCha20-Poly1305 chunks this way (age spec).
  • Avoid
    • RSA PKCS#1 v1.5 encryption: Bleichenbacher oracle (CRYPTO 1998), still found in 2018 (ROBOT, Böck et al., USENIX Security 2018).
    • Textbook RSA: c = m^e mod n (RFC 8017 section 5.1.1) is deterministic, so equal blocks give equal ciphertexts and guesses can be checked (our reasoning).
    • RFC 8017 section 7: OAEP is required for new applications; v1.5 is kept only for compatibility.
    • RSA per block over a file: slow, large, and blocks can be dropped or reordered undetected (our reasoning).
  • C APIs (OpenSSL 3.5)
    • HPKE: OSSL_HPKE_CTX_new, OSSL_HPKE_encap, OSSL_HPKE_seal; receiver OSSL_HPKE_decap, OSSL_HPKE_open (OSSL_HPKE_CTX_new(3)).
    • Raw KEM: EVP_PKEY_encapsulate_init, EVP_PKEY_encapsulate, EVP_PKEY_decapsulate (EVP_PKEY_encapsulate(3)).
    • RSA-OAEP: EVP_PKEY_encrypt after EVP_PKEY_CTX_set_rsa_padding(ctx, RSA_PKCS1_OAEP_PADDING) (EVP_PKEY_CTX_set_rsa_padding(3)).
/* HPKE base mode sender: enc and ct go to the recipient. */
int hpke_send(const unsigned char *rpub, size_t rpublen,
              const unsigned char *pt, size_t ptlen,
              unsigned char *enc, size_t *enclen,
              unsigned char *ct, size_t *ctlen) {
    /* X25519, HKDF-SHA256, AES-128-GCM (hpke.h) */
    OSSL_HPKE_SUITE suite = OSSL_HPKE_SUITE_DEFAULT;
    static const unsigned char info[] = "app v1 file";
    OSSL_HPKE_CTX *c = OSSL_HPKE_CTX_new(OSSL_HPKE_MODE_BASE, suite,
                           OSSL_HPKE_ROLE_SENDER, NULL, NULL);
    int ok = c != NULL
        && OSSL_HPKE_encap(c, enc, enclen, rpub, rpublen,
                           info, sizeof info - 1) == 1
        && OSSL_HPKE_seal(c, ct, ctlen, NULL, 0, pt, ptlen) == 1;
    OSSL_HPKE_CTX_free(c);
    return ok;
}
  • Misuse to spot
    • RSA_PKCS1_PADDING in EVP_PKEY_CTX_set_rsa_padding or RSA_public_encrypt: v1.5 encryption; see Attacks > RSA PKCS#1 v1.5 decryption oracle.

Signatures

  • Purpose and guarantee
    • Only the private key signs; anyone with the authentic public key verifies, so a third party can attribute the message (FIPS 186-5 section 1).
    • Guarantee: EUF-CMA, no valid signature on a new message without the key (Goldwasser, Micali, Rivest, SIAM J. Comput. 1988).
    • Not guaranteed: unique signatures (malleability), freshness (a signed message replays), confidentiality, or that the public key is the right one (our reasoning).
  • Picks
    • Ed25519 by default: deterministic nonce, 32-byte keys, 64-byte signatures, few edge cases (RFC 8032 section 5.1).
      • FIPS 186-5 (2023) approves EdDSA, so FIPS alone no longer rules it out where the module's validation covers it.
    • ECDSA P-256 when an HSM, cloud KMS, smartcard or WebAuthn authenticator forces it; derive k per RFC 6979.
    • RSA-PSS, 3072-bit, for RSA-only verifiers or legacy PKI (RFC 8017 section 8.1); large signatures and slow signing.
    • JWT names: EdDSA (RFC 8037; RFC 9864 deprecates it in favor of Ed25519), ES256, PS256.
  • Avoid
    • SHA-1 in signatures: SP 800-131A Rev 2 disallows it for signature generation.
    • DSA: FIPS 186-5 no longer approves it for signature generation.
    • ECDSA with an RNG k from a weak source: see Attacks > Weak or misused RNG.
  • Malleability (gap Q11)
    • From one valid signature anyone derives another valid one on the same message: ECDSA (r, n - s), BER vs DER encodings, Ed25519 S >= L (BIP 62; RFC 8032 section 5.1.7).
    • Not a forgery: EUF-CMA allows it, strong unforgeability (SUF-CMA) forbids it (Boneh, Shen, Waters, PKC 2006).
    • It bites when signature bytes act as an id: Bitcoin txids (fixed by BIP 66 strict DER and BIP 141 SegWit), replay caches, dedup keys.
    • Fix: key caches on the message hash; enforce low-S and strict DER; RFC 8032 section 5.1.7 requires rejecting S >= L.
  • C APIs (OpenSSL 3.5)
    • Sign: EVP_DigestSignInit then one-shot EVP_DigestSign; Ed25519 needs a NULL digest (EVP_DigestSignInit(3), EVP_SIGNATURE-ED25519(7)).
    • Verify: EVP_DigestVerifyInit, EVP_DigestVerify; 1 means valid, 0 invalid, negative an error (EVP_DigestVerifyInit(3)).
    • Deterministic ECDSA: set OSSL_SIGNATURE_PARAM_NONCE_TYPE ("nonce-type") to 1, OpenSSL 3.2+ (EVP_SIGNATURE-ECDSA(7)).
    • RSA-PSS: EVP_PKEY_CTX_set_rsa_padding(pctx, RSA_PKCS1_PSS_PADDING) on the signing context (EVP_PKEY_CTX_set_rsa_padding(3)).
/* Ed25519 verify; accept only an explicit 1. */
int ed25519_ok(EVP_PKEY *pub, const unsigned char *msg, size_t n,
               const unsigned char sig[64]) {
    EVP_MD_CTX *m = EVP_MD_CTX_new();
    int ok = m != NULL
        && EVP_DigestVerifyInit(m, NULL, NULL, NULL, pub) == 1
        && EVP_DigestVerify(m, sig, 64, msg, n) == 1;
    EVP_MD_CTX_free(m);
    return ok;
}
  • Misuse to spot
    • if (EVP_DigestVerify(..)) or if (ECDSA_verify(..)): a negative error code counts as valid.
      • OpenSSL's own callers had this bug (CVE-2008-5077); compare with == 1.

Key exchange

  • Purpose and guarantee
    • Two parties derive a shared secret over a public channel; unauthenticated ECDH resists only passive attackers (primitive_quiz_key.md Q13).
    • Not guaranteed: authentication. An active MITM runs one exchange with each side.
      • TLS 1.3 signs the transcript (CertificateVerify) and MACs it (Finished) (RFC 8446 sections 4.4.3, 4.4.4).
    • Forward secrecy needs ephemeral keys deleted after the handshake.
      • RSA key transport and static DH lack it; TLS 1.3 removed both (RFC 8446 section 1.2).
    • The raw output is not a uniform key: run it through HKDF with transcript context (RFC 5869; see the KDF section).
  • Picks
    • X25519 (RFC 7748): every 32-byte input lies on the curve or its secure twist, so no on-curve check is needed (Bernstein, PKC 2006).
      • RFC 7748 section 6.1: parties MAY reject an all-zero shared secret from small-order inputs.
    • ECDH P-256 where FIPS or hardware requires it, with full public key validation (SP 800-56A Rev 3 section 5.6.2.3).
    • Hybrid X25519MLKEM768 for post-quantum: see the Post-quantum section.
  • Avoid
    • Unvalidated P-256 peer points with a reused static key: see Attacks > Invalid curve and small subgroup.
    • Finite-field DH below 2048 bits or with custom groups: Logjam (Adrian et al., CCS 2015); use RFC 7919 ffdhe groups if FFDH is required.
    • Static-static DH alone: no forward secrecy and KCI-prone (Noise spec section 7.7, ss).
  • C APIs (OpenSSL 3.5)
    • Keygen: EVP_PKEY_Q_keygen(NULL, NULL, "X25519"); peer bytes: EVP_PKEY_new_raw_public_key(EVP_PKEY_X25519, ...) (EVP_PKEY_keygen(3), EVP_PKEY_new(3)).
    • Derive: EVP_PKEY_derive_init, EVP_PKEY_derive_set_peer (validates the peer key), EVP_PKEY_derive (EVP_PKEY_derive(3)).
/* X25519: shared secret into out[32]; feed it to HKDF, never use raw. */
int x25519_shared(EVP_PKEY *mine, EVP_PKEY *peer,
                  unsigned char out[32]) {
    size_t len = 32;
    EVP_PKEY_CTX *c = EVP_PKEY_CTX_new_from_pkey(NULL, mine, NULL);
    int ok = c != NULL
        && EVP_PKEY_derive_init(c) == 1
        && EVP_PKEY_derive_set_peer(c, peer) == 1
        && EVP_PKEY_derive(c, out, &len) == 1 && len == 32;
    EVP_PKEY_CTX_free(c);
    return ok;
}
  • Misuse to spot
    • DH output used directly as an AES key, or a handshake whose signature does not cover both key shares (MITM) (our reasoning; RFC 8446 section 4.4.3).

CSPRNG

  • Purpose and guarantee
    • Output is unpredictable to anyone without the internal state; reseeding from fresh entropy restores security after a state leak (SP 800-90A Rev 1).
    • Not guaranteed: unpredictability when seeded before the OS pool has entropy, or when state is cloned by fork or a VM snapshot.
      • First-boot keys shared primes across devices (Heninger et al., USENIX Security 2012); see Attacks > Weak or misused RNG.
  • Picks
    • Long-term keys: getrandom(2) with flags 0, which blocks until the pool is initialized, then never blocks (getrandom(2)).
    • arc4random_buf(3), glibc 2.36+: never fails, reads getrandom (glibc 2.36 NEWS; uncertain on the internal design).
    • OpenSSL RAND_bytes, RAND_priv_bytes (for private keys): a DRBG seeded from the OS (RAND_bytes(3), EVP_RAND(7)).
    • Linux reseeds on VM fork via vmgenid since 5.18 (version uncertain).
  • Avoid (gap Q15, in C terms)
    • rand(), random(), drand48(): not CSPRNGs; C11 7.22.2 makes no quality claim.
      • Their small state is recoverable from outputs; drand48 is a 48-bit LCG (drand48(3)).
    • A seed the attacker can enumerate: srand(time(NULL)), a pid, or any 32- or 64-bit seed fed to a DRBG.
      • Every key is then reproducible; Debian OpenSSL keys came from a pid-sized seed space (CVE-2008-0166).
    • getrandom with GRND_INSECURE for keys, or GRND_NONBLOCK with EAGAIN unhandled (getrandom(2)); RAND_pseudo_bytes, deprecated in 1.1.0 (openssl/rand.h).
  • C APIs
    • ssize_t getrandom(void *buf, size_t n, unsigned flags) from <sys/random.h> (getrandom(2)).
    • int RAND_bytes(unsigned char *buf, int num): 1 on success, 0 or -1 on failure (RAND_bytes(3)).
/* Fill buf from the kernel CSPRNG; 0 on success, -1 on error. */
int os_random(unsigned char *buf, size_t n) {
    while (n > 0) {
        ssize_t r = getrandom(buf, n, 0); /* blocks until seeded */
        if (r < 0) {
            if (errno == EINTR)
                continue;
            return -1;
        }
        buf += r;
        n -= (size_t)r;
    }
    return 0;
}
  • Misuse to spot
    • RAND_bytes(key, 32); with the return ignored, or if (RAND_bytes(..)), which treats -1 as success (RAND_bytes(3) RETURN VALUES).

Post-quantum

  • Purpose and guarantee
    • Resist a quantum attacker: Shor's algorithm breaks RSA, finite-field DH and ECC (Shor, FOCS 1994).
    • Grover gives only a square-root speedup on key search, so AES-256 and SHA-256 keep a wide margin (uncertain on exact NIST guidance).
    • Key exchange is urgent: harvest now, decrypt later. Traffic recorded today falls once a quantum computer exists (NIST IR 8547 ipd, 2024; uncertain).
    • Signatures can wait: a signature only has to resist forgery when verified, and past ones stay valid (our reasoning).
      • Exception: long-lived roots and firmware or secure-boot keys, which are slow to replace (NSA CNSA 2.0 puts firmware signing first; uncertain).
  • Picks (gap Q25)
    • Standards, August 2024: FIPS 203 ML-KEM (KEM); FIPS 204 ML-DSA and FIPS 205 SLH-DSA (signatures).
    • Firmware signing: stateful hash-based LMS or XMSS (SP 800-208); state reuse breaks them.
    • TLS: hybrid group X25519MLKEM768 (draft-ietf-tls-ecdhe-mlkem); Chrome enabled it by default in version 131 (2024; uncertain).
    • Hybrid holds if either X25519 or ML-KEM holds; hedge example: SIKE, a NIST round 4 candidate, fell classically (Castryck and Decru, 2022).
    • Sizes: ML-KEM-768 encapsulation key 1184 bytes, ciphertext 1088 bytes (FIPS 203 table 3).
  • Avoid
    • Dropping the classical half in a new protocol before ML-KEM has more analysis (hybrid rationale above; policy varies, e.g. CNSA 2.0, uncertain).
    • Porting DH designs that use static-static DH (ss): ML-KEM is a KEM, not a non-interactive key agreement (FIPS 203 section 3).
  • C APIs (OpenSSL 3.5)
    • OpenSSL 3.5.6 here lists ML-KEM-512/768/1024 and X25519MLKEM768 (openssl list -kem-algorithms), and ML-DSA, SLH-DSA signatures.
    • KEM: EVP_PKEY_Q_keygen(NULL, NULL, "ML-KEM-768"), then EVP_PKEY_encapsulate / EVP_PKEY_decapsulate (EVP_PKEY-ML-KEM(7)).
    • TLS: SSL_CTX_set1_groups_list(ctx, "X25519MLKEM768:X25519") (SSL_CTX_set1_groups_list(3)).
/* ML-KEM-768 encapsulate: ct goes to the peer, ss stays local. */
int mlkem_encap(EVP_PKEY *peer, unsigned char ct[1088],
                unsigned char ss[32]) {
    size_t ctlen = 1088, sslen = 32;
    EVP_PKEY_CTX *c = EVP_PKEY_CTX_new_from_pkey(NULL, peer, NULL);
    int ok = c != NULL
        && EVP_PKEY_encapsulate_init(c, NULL) == 1
        && EVP_PKEY_encapsulate(c, ct, &ctlen, ss, &sslen) == 1;
    EVP_PKEY_CTX_free(c);
    return ok;
}
  • Misuse to spot
    • Treating a successful ML-KEM decapsulation as proof the ciphertext is genuine.
      • Implicit rejection returns a pseudorandom key for a bad ciphertext, not an error (FIPS 203 section 6.3); authenticate later, e.g. a key confirmation MAC.

Noise protocol patterns

Noise builds a handshake from DH tokens; the pattern name says which static keys exist and how each reaches the peer. Source: Noise spec revision 34 (noiseprotocol.org/noise.html), cited below as "spec".

Tokens

  • e: the sender makes a fresh ephemeral key pair and sends the public key in clear (spec section 5.3).
  • s: the sender sends its static public key, encrypted once a key exists (spec section 5.3).
  • ee: DH of both ephemerals; gives forward secrecy, no authentication (spec section 7.7).
  • es: DH of the initiator's ephemeral and the responder's static.
    • Authenticates the responder: only the holder of its static key derives the later keys (spec section 7.7).
    • Without ee, a later theft of the responder's static key decrypts the payload (spec section 7.7).
  • se: DH of the initiator's static and the responder's ephemeral; authenticates the initiator, mirror of es (spec section 7.7).
  • ss: DH of both statics; authenticates both, but gives no forward secrecy and is KCI-prone (spec section 7.7).
  • psk: MixKeyAndHash(psk) of a 32-byte shared secret (spec section 9).
    • psk0 puts it at the start of message 1; psk1, psk2 at the end of message 1, 2 (spec section 9.4).
    • Validity rule: no encrypted data after psk unless the party has sent e (spec section 9.3).

Pattern naming

  • -> is initiator to responder, <- the reverse; lines before ... are pre-messages, keys known in advance (spec section 7.1).
  • First letter is the initiator's static key, second the responder's (spec section 7.5).
    • N: no static key.
    • K: static key known to the peer in advance (a pre-message).
    • X: static key transmitted during the handshake, encrypted.
    • I: initiator only; static key sent immediately in message 1, with reduced or no identity hiding.
  • One-way patterns N, K, X name only the sender's static; the recipient's static is always pre-known (spec section 7.4).
  • Patterns ending in K allow 0-RTT: the initiator encrypts its first payload (spec section 7.5).

Common patterns

Flows copied from spec sections 7.4 (one-way) and 7.5 (interactive).

  • NN: -> e <- e, ee: both anonymous; forward secrecy but no authentication, so an active MITM wins.
  • NK: <- s ... -> e, es <- e, ee: initiator knows the responder's key; responder authenticated, initiator anonymous.
  • XX: -> e <- e, ee, s, es -> s, se: mutual auth with no prior keys; 3 messages.
  • IK: <- s ... -> e, es, s, ss <- e, ee, se: mutual auth with 0-RTT; initiator static sent in message 1, encrypted to the responder static.
  • KK: -> s <- s ... -> e, es, ss <- e, ee, se: both statics pre-known; mutual auth with 0-RTT.
  • XK: <- s ... -> e, es <- e, ee -> s, se: initiator knows the responder key; initiator static sent in message 3 with forward secrecy.
  • IX: -> e, s <- e, ee, se, s, es: initiator static sent in clear in message 1.
  • N: <- s ... -> e, es: one-way; anonymous sender to a known recipient.
  • K: -> s <- s ... -> e, es, ss: one-way; sender static pre-known, sender authenticated only by ss.
  • X: <- s ... -> e, es, s, ss: one-way; sender static sent encrypted, sender authenticated only by ss.

Use cases

  • WireGuard: Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s (wireguard.com/protocol).
    • IK fits since peer static keys are configured; the psk2 key is optional and added for post-quantum resistance (uncertain).
  • Lightning: Noise_XK_secp256k1_ChaChaPoly_SHA256 (BOLT 8, 08-transport.md in github.com/lightning/bolts).
    • XK fits since a node dials a known node key; the initiator's key is sent in message 3 with forward secrecy (spec section 7.8).
  • WhatsApp client to server: Noise Pipes with Curve25519, AES-GCM and SHA256 (WhatsApp Security Whitepaper, "Transport Security").
    • Noise Pipes: XX for the first contact, IK for 0-RTT with the cached server key (spec section 10.4).
    • XXfallback when the responder cannot decrypt the IK message, e.g. after a server key change (spec section 10.4).
    • The whitepaper names Noise Pipes only, not the patterns; mapping to the three patterns is from spec section 10.4.

Security properties

  • Identity hiding, initiator / responder values from the spec section 7.8 table:
    • XX: initiator 8, encrypted with forward secrecy to an authenticated party; responder 1, forward secret but probeable by an anonymous initiator.
    • IK: initiator 4, encrypted to the responder static without forward secrecy; responder 3, not sent but a passive attacker can test candidate keys.
    • XK: initiator 8; responder 3.
    • KK: both 5, not sent, but a passive attacker can test candidate (responder private key, initiator public key) pairs.
    • IX: initiator 0, sent in clear; responder 6, encrypted with weak forward secrecy.
    • NK, N: responder 3; X: initiator 4, responder 3; K: both 5.
  • Forward secrecy comes from ee: payloads sent after it survive later static key theft (spec section 7.7, destination properties).
  • KCI: sender auth only via ss can be forged by anyone holding the recipient's static key (spec section 7.7, source property 1).
    • Sender auth via DH of the sender's static and the recipient's ephemeral resists KCI (spec section 7.7, source property 2).
    • So the first messages of IK, KK, K and X authenticate the initiator only by ss, before any ee, and are KCI-prone.
  • 0-RTT payloads (first message of a pattern ending in K) are encrypted with es/ss only (spec section 7.7, destination property 2).
    • No forward secrecy if the recipient's static key is later stolen.
    • Replayable, since the recipient contributed no ephemeral; the application must tolerate or detect replays.
  • Patterns starting with K or I give the responder only weak forward secrecy until it receives a transport message (spec section 7.5).
  • Interview line: pick the pattern by who knows whose static key: XX with none, IK for 0-RTT as WireGuard does.
    • ee gives forward secrecy; anything before it, such as 0-RTT data or ss-only auth, is replayable, not forward secret, and KCI-prone.

X3DH (Extended Triple Diffie-Hellman)

X3DH lets Alice derive a shared key with an offline Bob from keys he published to a server. Source: Signal X3DH spec (signal.org/docs/specifications/x3dh/), cited below as "X3DH spec".

Keys

  • IK: long-term identity key of each party (X3DH spec section 2.4).
  • SPK: Bob's signed prekey, rotated periodically; Bob publishes Sig(IK_B, Encode(SPK_B)), an XEdDSA signature.
    • Alice verifies the signature and aborts on failure (X3DH spec sections 3.2, 3.3).
  • OPK: Bob's one-time prekeys, each used in one run; the bundle may run out of them (X3DH spec sections 2.4, 3.2).
  • EK: Alice's ephemeral key, fresh per run (X3DH spec section 2.4).

DH computations

  • DH1 = DH(IK_A, SPK_B), DH2 = DH(EK_A, IK_B), DH3 = DH(EK_A, SPK_B) (X3DH spec section 3.3).
  • DH4 = DH(EK_A, OPK_B), only if the bundle has an OPK (X3DH spec section 3.3).
  • DH1 and DH2 give mutual authentication; DH3 and DH4 give forward secrecy (X3DH spec section 3.3).
  • DH4 also stops replay of the initial message, since Bob deletes the OPK after one use (X3DH spec section 4.2).

Key derivation

  • SK = KDF(DH1 || DH2 || DH3 [|| DH4]), 32 bytes of HKDF output (X3DH spec sections 2.2, 3.3).
    • HKDF input is F || KM, F = 32 bytes of 0xFF for X25519, for domain separation from XEdDSA (X3DH spec section 2.2).
    • Salt is zeros of hash length; info is an application-specific ASCII string (X3DH spec section 2.2).
  • AD = Encode(IK_A) || Encode(IK_B), the AEAD associated data of the initial message (X3DH spec section 3.3).
    • Applications may append more identity data, such as usernames or certificates (X3DH spec section 3.3).

Properties and risks

  • Async setup: Bob can be offline; he publishes IK, signed SPK and OPKs to a server first (X3DH spec sections 1, 3.2).
  • Deniability: no publishable cryptographic proof of who talked (X3DH spec section 4.4).
    • Weaker if a party collaborates with a third party during the run (X3DH spec section 4.4).
  • No OPK: a replayed initial message is accepted (X3DH spec section 4.2).
    • The post-X3DH protocol must randomize its key before Bob sends data, or keys are reused (X3DH spec section 4.3).
  • SPK compromise: with IK_B and SPK_B private keys and no OPK, an attacker recovers earlier SKs (X3DH spec section 4.6).
    • Mitigation: rotate SPK often (X3DH spec section 4.6).
  • Server: can drain OPKs to weaken forward secrecy; rate-limit prekey fetches (X3DH spec section 4.7).
  • Identity keys must be compared out of band (fingerprints, QR codes), or there is no guarantee of the peer (X3DH spec section 4.1).
    • Signal's app calls the comparison "safety numbers"; the spec does not use that term (uncertain).
  • Successor PQXDH adds a signed KEM prekey (Kyber-1024 example) to stop harvest-now-decrypt-later (PQXDH spec sections 2.1, 4.7).
    • Its authentication still relies on discrete log, so it is not quantum-secure (signal.org/docs/specifications/pqxdh/ sections 1, 4.1).
  • Interview line: X3DH mixes 3-4 DHs over identity, signed and one-time prekeys so an offline peer gets mutual auth and forward secrecy.
    • Without a one-time prekey the first message is replayable, and safety numbers must be verified or the server can MITM.

Double Ratchet

The Double Ratchet derives a fresh key per message from a shared secret, combining KDF chains with a DH ratchet. Source: Signal Double Ratchet spec (signal.org/docs/specifications/doubleratchet/), cited below as "DR spec".

Keys

  • Root key RK: fed by DH outputs; each step outputs a new chain key (DR spec sections 2.3, 3.2).
  • Chain keys CKs, CKr: sending and receiving KDF chains (DR spec section 3.2).
  • Message key: unique per message, derived from a chain key and never used to derive other keys (DR spec section 2.2).
  • Recommended KDFs (DR spec section 7.2):
    • KDF_RK: HKDF with RK as salt and the DH output as input key material.
    • KDF_CK: HMAC keyed by CK; input 0x01 gives the message key, 0x02 the next chain key.

The two ratchets

  • Symmetric-key ratchet: each message advances its chain one step: CK -> (next CK, message key) (DR spec section 2.2).
  • DH ratchet: each message carries the sender's ratchet public key (DR spec section 2.3).
    • A new peer key triggers a DH; its output feeds KDF_RK, which resets the sending and receiving chains.
    • Parties take turns replacing ratchet key pairs, so a leaked private key is eventually replaced.

Security properties

  • Forward secrecy: the chain KDF is one-way and used message keys are deleted (DR spec sections 2.1, 2.2).
    • So a later leak of a chain key does not reveal past message keys.
  • Post-compromise security (break-in recovery): fresh DH outputs mix new entropy into RK (DR spec sections 2.1, 2.3).
    • So an attacker who stole state loses access after the next DH step, if passive (DR spec section 8.2).
    • The symmetric chains alone give no break-in recovery (DR spec section 2.2).
    • An active attacker with stolen keys can keep impersonating; the party must replace keys (DR spec section 8.2).

Out-of-order messages

  • Header carries N (message number) and PN (previous chain length) (DR spec section 2.6).
    • The receiver advances its chain and stores skipped message keys for late messages.
  • MAX_SKIP caps skipped keys per chain so a malicious sender cannot force excess computation (DR spec section 3.1).
  • Stored skipped keys cost storage and expose recorded messages if the device is later compromised (DR spec section 8.4).
    • Mitigation: a per-session limit (spec example 1000) and deletion after a time or event (DR spec section 8.4).

Header encryption and X3DH pairing

  • Header encryption variant hides which session a message belongs to and its order (DR spec section 4).
    • Adds header keys HKs, HKr and next header keys NHKs, NHKr.
    • A header that decrypts with a next header key signals a DH ratchet step.
  • Pairing: the key agreement's SK becomes the initial root key and its AD is used for ratchet AEAD (DR spec section 7.1).
    • Bob's SPK becomes his initial ratchet public key (DR spec section 7.1).
    • The current spec names PQXDH here; X3DH plugs in the same way, as earlier spec revisions described (uncertain).

Risks

  • Key storage: guarantees fail if deleted keys or plaintext are recoverable from the device (DR spec section 8.1).
  • State rollback: restoring an old state (e.g. a backup) re-derives deleted keys and may reuse message keys (uncertain).
    • The spec does not address rollback; on a failed decrypt it discards state changes (DR spec section 3.5).
  • Interview line: KDF chains give per-message forward secrecy, and the DH ratchet mixes in fresh entropy for break-in recovery.
    • MAX_SKIP bounds skipped keys against DoS; old ratchet state must never be restored.

Authentication and key exchange

These attacks work because a handshake does not bind keys to the right peer, role or channel. Defense: authenticate the full transcript, identities and roles, with fresh ephemeral keys.

Unauthenticated key exchange and MITM (KEM/DH, auth)

  • Root cause
    • Key exchange alone gives a shared key with someone, not with the intended peer; anonymous DH is secure only against passive eavesdroppers.
      • An active attacker runs one DH with each side and relays, reading and editing everything.
    • Peer authentication is skipped or weakened: certificate checks disabled, hostnames unchecked, trust on first use (TOFU) without a pinned fingerprint, an unsigned handshake.
    • Source: RFC 8446 section 4.4 (TLS 1.3 authenticates with CertificateVerify and Finished); RFC 9525 (service identity checks).
  • Impact
    • Breaks peer authentication: the attacker holds one session key with each side, and each side believes it talks to the other (RFC 8446 appendix E.1).
    • Attacker reads and edits all traffic and captures credentials sent over it, so confidentiality and integrity fail too (Beurdouche et al., IEEE S&P 2015).
  • Spot in C code
    • OpenSSL: SSL_CTX_set_verify(ctx, SSL_VERIFY_NONE, NULL), or a verify callback that always returns 1 (SSL_CTX_set_verify(3)).
    • OpenSSL: chain verified but no hostname check; the call SSL_set1_host(ssl, name) (or X509_check_host) is absent (SSL_set1_host(3)).
    • OpenSSL: SSL_get_verify_result ignored after the handshake, since without SSL_VERIFY_PEER a failed chain does not abort.
    • libcurl: CURLOPT_SSL_VERIFYPEER set to 0 or CURLOPT_SSL_VERIFYHOST set to 0 (libcurl docs).
    • A hand-rolled handshake that exchanges X25519 public keys (EVP_PKEY_get_raw_public_key) with no signature, MAC or pinned identity key over them.
  • Design defense
    • Authenticate the key exchange: sign the transcript with a long-term key the peer already trusts, or use a PSK or a Noise pattern with static keys (Noise spec, noiseprotocol.org).
    • Validate chain, hostname, expiry and revocation policy; pin a key or CA only when you control both ends and plan rotation.
    • Use mutual TLS or an application-layer signature when the server must identify clients (RFC 8446 section 4.3.2 CertificateRequest).
    • Keep verification-off switches out of release builds.
  • Known attacks:
    • SKIP-TLS and SMACK (2015, TLS state machines): clients accepted handshakes that skipped ServerKeyExchange or CertificateVerify, allowing impersonation (Beurdouche et al., IEEE S&P 2015).
    • Disabled certificate validation in app code is a recurring finding (CWE-295, uncertain as a named source).
    • SSH TOFU: users accept an unknown host key at first connect (OpenSSH behavior, uncertain citation).
  • Sources
    • RFC 8446 section 4.4 and appendix E.1; RFC 9525; Beurdouche et al., IEEE S&P 2015.

Reflection (MAC, auth)

  • Root cause
    • The attacker returns a party's own message (challenge, tag or ciphertext) to it, and the receiver accepts it as coming from the peer.
    • It works when both directions use the same key and message format, with no role, direction or identity in the authenticated data.
    • Textbook case: mutual challenge-response with a shared key. The attacker opens a second session and has the victim answer its own challenge.
      • Source: Boyd and Mathuria, "Protocols for Authentication and Key Establishment" (section uncertain).
  • Impact
    • Breaks message origin authentication: a valid MAC no longer proves the peer sent the message, since the victim's own tag verifies.
    • Attacker passes challenge-response login without the key, or makes a party accept its own message as the peer's (MS08-068; Drucker and Gueron, ePrint 2019/347).
  • Spot in C code
    • One key buffer used with HMAC() or an AEAD for both client-to-server and server-to-client messages.
    • Tag input is only the payload: no role byte, no sender id, no direction label.
    • Both sides use a counter nonce starting at zero under the same key: reflected or concurrent messages collide on a nonce (see nonce reuse).
    • A responder that signs or MACs whatever challenge it receives, even one it generated itself.
  • Design defense
    • Derive separate keys per direction with HKDF info labels; TLS 1.3 has distinct client and server traffic secrets and Finished keys (RFC 8446 section 7.1).
    • OpenSSL 3: derive both keys from one secret via EVP_KDF_fetch(NULL, "HKDF", NULL) with distinct info, such as c2s and s2c (EVP_KDF-HKDF(7)).
    • Put the sender role, both identities and a session id inside every MAC, signature or AEAD associated data.
    • A responder rejects a challenge equal to one it issued; bind each response to the challenge's origin.
  • Known attacks:
    • SMB NTLM reflection (2008, Windows SMB): the attacker returned a victim's NTLM challenge-response to the victim's own SMB server (MS08-068, CVE-2008-4037).
      • Related: the later NTLM relay family; the exact CVE mapping is uncertain, verify before quoting.
    • Selfie (2019, TLS 1.3 external PSK): with one PSK shared by a group, the attacker reflects a client's ClientHello back to it, so it talks to itself (Drucker and Gueron, IACR ePrint 2019/347).
  • Sources
    • RFC 8446 section 7.1; ISO/IEC 9798 discussion of reflection (uncertain, not re-fetched).

Unknown key share and missing identity binding (KEM/DH, auth)

  • Root cause
    • The handshake authenticates keys or key shares but not who each side believes the peer is.
      • Result: A and B share a key, but at least one of them believes it shares that key with someone else, such as the attacker.
    • Typical flaw: a signature covers the DH values but not the peer's identity, so an attacker registers the victim's public key under its own name.
      • Source: Blake-Wilson and Menezes, "Unknown key-share attacks on the station-to-station protocol", PKC 1999.
    • Related: the TLS triple handshake attack used session resumption to make two connections share a master secret (Bhargavan et al., IEEE S&P 2014).
  • Impact
    • Breaks identity binding in peer authentication: the key is shared with the right party, but one side holds the wrong partner identity.
    • Attacker gains credit or authority: B credits A's messages to the attacker, or client auth on one connection carries to another (Blake-Wilson and Menezes 1999; Bhargavan et al. 2014).
  • Spot in C code
    • A signature over only the ephemeral public key or only a nonce: EVP_DigestSign(mctx, sig, &siglen, eph_pub, 32) with nothing else in the input.
    • KDF call with a constant info or context and no party identifiers or transcript hash.
    • Identity registration that lets any caller bind an existing public key to a new name (no proof of possession of the private key).
    • A resumption or session-ticket path that does not re-bind to the original peer identity.
  • Design defense
    • Sign or MAC the whole transcript including both identities and key shares; TLS 1.3 signs a hash of the handshake including the certificates (RFC 8446 section 4.4.3).
    • Put party identifiers in the KDF context (NIST SP 800-56A Rev 3, key derivation OtherInfo/FixedInfo; section number uncertain).
    • Add key confirmation (a MAC over the transcript under the new key), as TLS Finished does (RFC 8446 section 4.4.4).
    • Require proof of possession of the private key at registration.
    • TLS 1.2 fix for the triple handshake: the extended master secret (RFC 7627).
  • Known attacks:
    • Lowe's attack on Needham-Schroeder (1995, Needham-Schroeder public key): message 2 omits B's identity, so an insider relays A's run and B believes it talks to A (Lowe, TACAS 1996).
    • STS unknown key share (1999, station-to-station): the attacker certifies the victim's public key under its own name (Blake-Wilson and Menezes, PKC 1999).
    • MQV unknown key share (2001, MQV key agreement): an online UKS attack on the protocol as specified (Kaliski, ACM TISSEC 2001 (uncertain)).
    • Triple Handshake (3SHAKE) (2014, TLS 1.2 resumption and renegotiation): the attacker syncs master secrets of two connections, so client auth on one carries to the other; fixed by RFC 7627.
      • Source: Bhargavan et al., IEEE S&P 2014.
  • Sources
    • Blake-Wilson and Menezes, PKC 1999; Bhargavan et al., IEEE S&P 2014; RFC 8446 sections 4.4.3, 4.4.4 and appendix E.1; RFC 7627.

Missing channel binding (protocol, auth)

Inner authentication run inside TLS is not tied to that TLS channel, so a MITM relays it onto its own connection.

  • Root cause
    • A secret or credential is authenticated at the application layer but not tied to the secure channel it travels over (RFC 5056 section 1).
      • Inner auth types: password, bearer token, SAML or OAuth response, NTLM, Kerberos, SCRAM or EAP challenge-response.
    • The inner auth proves "I know the secret" but not "over this TLS channel"; each layer is secure alone, the composition is not.
    • How it works (Asokan, Niemi, Nyberg, 2003; venue uncertain):
      • 1. The client opens TLS to the attacker (phishing link or lax certificate check).
      • 2. The attacker opens its own TLS to the real server.
      • 3. The attacker forwards the inner auth messages unchanged.
      • 4. The server binds the authenticated identity to the attacker's TLS session.
    • Bearer tokens stolen from logs or proxies are replayed on a new connection (RFC 6750 section 5).
    • TLS 1.2 renegotiation: a full new handshake inside the existing connection, its messages encrypted under the current keys.
      • Afterwards new keys and parameters apply, and the TCP and application session continues.
      • Client-initiated: a new ClientHello. Server-initiated: HelloRequest.
      • Uses: a client certificate mid-connection (e.g. only for /admin), a cipher change, a rekey.
      • Flaw: before RFC 5746 the new handshake is not bound to the previous one, so a MITM splices a victim's handshake onto its own connection.
  • Impact
    • Breaks client authentication: the credential proves who the user is but not which channel is theirs, so the server accepts it on the attacker's connection.
    • Attacker gets a session as the victim without learning the credential, via relayed NTLM or EAP logins.
      • Also via replayed bearer tokens or injected prefixes (RFC 5056 section 1; RFC 6750 section 5; CVE-2009-3555).
    • TLS 1.2 renegotiation: the server runs the victim's authenticated request as a continuation of the attacker's prefix (CVE-2009-3555).
      • Each renegotiation costs the server a public-key op, so client-initiated floods exhaust its CPU (THC-SSL-DOS, 2011).
  • Spot in C code
    • Password, token or challenge-response check over TLS that never reads the TLS session.
      • No SSL_export_keying_material call, and no hash of the peer certificate in the auth proof.
    • Token issued as a plain random string or unbound JWT with no cnf (confirmation) claim.
    • TLS-terminating proxies that forward identity in a header the backend trusts blindly.
    • OpenSSL renegotiation: SSL_renegotiate() starts one; SSL_OP_NO_RENEGOTIATION disallows all renegotiation (ssl.h).
      • SSL_get_secure_renegotiation_support() reports whether the peer supports RFC 5746 (ssl.h).
      • Red flag: SSL_OP_ALLOW_UNSAFE_LEGACY_RENEGOTIATION permits renegotiation with peers lacking RFC 5746.
      • Server flag: SSL_OP_ALLOW_CLIENT_RENEGOTIATION re-enables client-initiated renegotiation (off by default in 3.x, uncertain).
  • Design defense
    • Bind a channel-unique value into the inner auth proof.
      • tls-exporter (RFC 9266, TLS 1.3), built on exporters (RFC 5705; RFC 8446 section 7.5).
      • tls-server-end-point (RFC 5929): a hash of the server certificate.
      • OpenSSL: SSL_export_keying_material(3) derives the tls-exporter value.
      • The old tls-unique binding (RFC 5929) is unsafe without the extended master secret; prefer tls-exporter.
    • tls-exporter: a channel binding type over the exporter above, not a TLS extension.
      • TLS-Exporter(label, context, length) derives bytes from the connection's secrets.
      • tls-exporter uses label "EXPORTER-Channel-Binding", an empty context and 32 bytes (RFC 9266).
      • A MITM's two connections have different secrets, so the values differ and a relayed login fails.
      • OpenSSL: SSL_export_keying_material(ssl, out, 32, "EXPORTER-Channel-Binding", 24, NULL, 0, 0).
      • On TLS 1.2, RFC 9266 requires EMS, because without it two connections can share a master secret.
    • Extended Master Secret (EMS): the TLS 1.2 extension extended_master_secret (RFC 7627).
      • Old: master_secret = PRF(pms, "master secret", client_random + server_random).
        • So the certificate, cipher suite and key exchange parameters are not bound.
      • Triple Handshake: a MITM forwards the same pms and randoms, so two connections share a master secret.
        • tls-unique then collides; resumption plus renegotiation let the MITM impersonate the client.
      • EMS: master_secret = PRF(pms, "extended master secret", session_hash).
        • session_hash is the transcript hash through ClientKeyExchange.
      • TLS 1.3 builds this in: its key schedule mixes in the transcript hash (RFC 8446 section 7.1).
        • That is why RFC 9266 replaced tls-unique with tls-exporter.
      • OpenSSL: SSL_get_extms_support() reports peer support; EMS is on by default since 1.1.0 (uncertain).
    • Use SCRAM -PLUS variants, which carry the channel binding (RFC 5802; RFC 7677).
    • Sender-constrain tokens: mutual-TLS certificate-bound tokens (RFC 8705) or DPoP proofs (RFC 9449).
    • Short token lifetimes and audience restriction narrow the damage of a stolen bearer token (RFC 8725, section number uncertain).
    • TLS 1.2 renegotiation: RFC 5746 renegotiation_info (or TLS_EMPTY_RENEGOTIATION_INFO_SCSV) carries the previous Finished verify_data.
      • This binds each renegotiation to the prior handshake; Triple Handshake later bypassed it via resumption, fixed by EMS (above).
      • Servers disable client-initiated renegotiation to stop DoS floods.
    • TLS 1.3 removed renegotiation (RFC 8446 section 1.2, uncertain): KeyUpdate rekeys (section 4.6.3).
      • Post-handshake auth requests a client certificate (section 4.6.2); a new connection changes parameters.
  • Known attacks:
    • SMBRelay (2001, NTLM over SMB): an NTLM exchange is relayed to another server; Extended Protection later added channel binding (Sir Dystic, 2001 (uncertain)).
      • The same relay targets HTTPS and LDAPS, where Microsoft Extended Protection for Authentication (EPA) binds NTLM to the TLS channel.
    • Tunneled authentication MITM (2003, PEAP and other EAP tunnels): inner credentials not bound to the outer TLS tunnel are relayed into another tunnel.
      • Source: Asokan, Niemi, Nyberg, 2003 (venue uncertain; an IACR ePrint version dates from 2002, uncertain).
    • TLS renegotiation attack (2009, TLS up to 1.2): the attacker sends a prefix, then the victim's handshake renegotiates the same connection and the server joins both; fixed by RFC 5746.
      • The MITM opens TLS to the server and sends e.g. GET /transfer?to=attacker plus an unterminated X-Ignore: header.
      • It splices the victim's ClientHello in as a renegotiation; the victim's authenticated request completes the prefix: request injection.
      • Root cause: the new handshake is not bound to the previous one; Triple Handshake (2014, below) later bypassed RFC 5746.
      • Source: Marsh Ray, 2009; CVE-2009-3555.
    • THC-SSL-DOS (2011, TLS up to 1.2): client-initiated renegotiation floods; each one costs the server a public-key op, so servers disable it.
      • Source: The Hacker's Choice, 2011 (uncertain).
    • Triple Handshake (2014): also made tls-unique collide across two connections, fixed by RFC 7627; see Unknown key share and missing identity binding.
      • Source: Bhargavan et al., IEEE S&P 2014.
    • PetitPotam (2021, NTLM relay to AD CS): coerced domain controller authentication relayed to HTTP enrollment endpoints without channel binding (CVE-2021-36942 (mapping uncertain)).
  • Sources
    • RFC 5056, RFC 5929, RFC 9266, RFC 5802, RFC 7677, RFC 8705, RFC 9449, RFC 7627; OpenSSL SSL_export_keying_material(3).
    • RFC 5705; RFC 8446 sections 7.1 and 7.5; OpenSSL SSL_get_extms_support(3).
    • RFC 5746; CVE-2009-3555; RFC 8446 section 1.2 (uncertain).
  • Interview line: inner auth not bound to the outer TLS channel can be relayed by a MITM; bind it to a channel value such as tls-exporter (RFC 9266), as SCRAM-PLUS and EPA do.
  • Interview line: EMS binds the TLS 1.2 master secret to the handshake transcript; tls-exporter derives a per-connection value from it so inner auth can bind to the channel.
  • Interview line: TLS 1.2 renegotiation nests a new handshake in the old one; unbound, it allowed prefix injection (2009), fixed by RFC 5746 and EMS; TLS 1.3 uses KeyUpdate and post-handshake auth.

Key compromise impersonation (KCI) (KEM/DH, auth)

  • Root cause
    • After an attacker steals party A's long-term key, it can impersonate other parties to A, not only A to others.
    • It arises when A authenticates peers with a key A itself can compute: static-static DH, a shared MAC key, a PSK.
    • Source: Blake-Wilson, Johnson, Menezes, "Key agreement protocols and their security analysis", 1997.
  • Impact
    • Breaks peer authentication for A after A's own long-term key leaks: A accepts the attacker as any peer (RFC 8446 appendix E.1, KCI resistance).
    • Attacker runs a MITM on A's sessions and reads what A sends to "the server", not only signs as A (Hlauschek et al., WOOT 2015).
  • Spot in C code
    • Mutual authentication built only from static-static DH: EVP_PKEY_derive with both EVP_PKEYs long-term.
    • A symmetric PSK that both sides hold as the only authenticator (inherently KCI-prone: whoever has the PSK is any peer).
    • Client authentication by a shared HMAC key where the server also holds that key.
  • Design defense
    • Authenticate with a signature by the peer's private key over the transcript; TLS 1.3 certificate authentication does this (RFC 8446 section 4.4.3).
    • In Noise, pick patterns whose payload-security table resists KCI and mixes an ephemeral key (Noise spec section 7.7; section number uncertain).
    • Store the long-term key in an HSM or enclave and use per-session ephemeral keys so a stolen key cannot be used by itself.
    • Revoke and rotate on compromise.
  • Known attacks:
    • KCI against TLS (2015, TLS 1.2 fixed (EC)DH client certificates): with the client's certificate key, an attacker impersonates any server to that client (Hlauschek et al., WOOT 2015).
  • Sources
    • Blake-Wilson, Johnson, Menezes, 1997; Hlauschek et al., WOOT 2015; RFC 8446 section 4.4.3 and appendix E.1.

Missing forward secrecy (KEM/DH, forward secrecy)

  • Root cause
    • Session keys depend on a long-term secret, so one later theft decrypts all recorded traffic.
    • RSA key transport encrypts the premaster secret to the server key; static-static DH has the same property.
    • Long-lived session ticket keys, resumption secrets and PSKs are also long-term secrets (Springall et al., "Measuring the Security Harm of TLS Crypto Shortcuts", IMC 2016; title from memory).
  • Impact
    • Breaks forward secrecy: theft of the long-term key, ticket key or PSK reveals session keys of past recorded sessions (RFC 8446 appendix E.1).
    • Attacker who recorded ciphertext decrypts all of it after one key theft or legal demand, so past confidentiality fails (Springall et al., IMC 2016).
  • Spot in C code
    • A key exchange using one X25519 or EC key generated at startup and used for every session (EVP_PKEY_keygen once).
    • Encrypting a session key to the peer's RSA public key (EVP_PKEY_encrypt, RSA_public_encrypt); RSA key-exchange suites in the cipher list.
    • Ephemeral key kept in a global or struct for reuse across sessions.
    • A ticket-encryption key that never rotates (OpenSSL ticket key callback or SSL_CTX_set_tlsext_ticket_keys).
    • Session keys logged, or not wiped after use (memset without OPENSSL_cleanse(3) or explicit_bzero(3)).
  • Design defense
    • Fresh ephemeral (EC)DH per session, deleted after use; all TLS 1.3 key exchange is ephemeral (RFC 8446 section 1.2).
    • Rotate ticket keys often and limit resumption lifetime.
    • Messaging uses a ratchet for forward secrecy and post-compromise security (Signal Double Ratchet specification).
    • Wipe secrets with OPENSSL_cleanse(3) or explicit_bzero(3); plain memset can be removed by the optimizer.
  • Known attacks:
    • Lavabit key demand (2013, TLS server key): a compelled server private key would decrypt all recorded non-FS sessions (court filings, 2013 (uncertain)).
    • Heartbleed (2014, TLS in OpenSSL): the heartbeat handler trusted the payload length and memcpy'd past the buffer, leaking memory including private keys (CVE-2014-0160; RFC 6520).
      • Without forward secrecy, a leaked RSA key decrypts recorded past traffic.
    • Session ticket key reuse (2016, TLS 1.2 resumption): long-lived ticket keys let one key theft decrypt many past sessions (Springall et al., IMC 2016).
  • Sources
    • RFC 8446 section 1.2 and appendix E.1; Springall et al., IMC 2016; CVE-2014-0160; Signal Double Ratchet specification.

Negotiation and message state

These attacks replay, reorder, drop or move a message or option outside the state it was made for. Defense: authenticate negotiation, sequence, freshness and context with each message.

Protocol downgrade (protocol, integrity)

  • Root cause
    • Peers negotiate version or ciphers in the clear, and still support weak options for compatibility, so an on-path attacker steers both to the weakest common choice.
      • Source: Beurdouche et al., IEEE S&P 2015; Adrian et al., CCS 2015.
    • Fallback retries (resend a ClientHello with a lower version after a failure) let the attacker cause the failure (RFC 7507 section 1).
    • The negotiation messages are not covered by a MAC or signature that is verified under strong keys (RFC 8446 section 4.4.4 shows the fix: Finished covers them).
  • Impact
    • Integrity of the negotiation breaks: both peers believe they agreed on strong parameters, but the attacker chose weak ones and neither side detects it.
      • Source: Beurdouche et al., IEEE S&P 2015; Adrian et al., CCS 2015.
    • The attacker then breaks the weak choice (512-bit RSA or DH, SSL 3.0 CBC) and reads or forges the session's traffic (FREAK, Logjam, POODLE in Known attacks below).
      • Source: Beurdouche et al., IEEE S&P 2015; Adrian et al., CCS 2015; RFC 7568.
    • Without a downgrade, the same attacker cannot break the strong options both peers support; the gain comes only from the negotiation (uncertain).
  • Spot in C code
    • OpenSSL: no SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION), or SSLv23_method/SSL_OP_ALL defaults with legacy versions and suites left on (SSL_CTX_set_min_proto_version(3)).
    • Cipher lists containing EXPORT, RC4, 3DES, NULL or aNULL, and DH parameters of 1024 bits or less.
    • A client that retries SSL_connect with a lower version after failure.
    • Own protocol: a version byte read before authentication and used to select looser parsing, with no minimum.
    • Negotiated parameters not included in the data passed to the signature or key derivation.
  • Design defense
    • Remove weak options instead of negotiating them; set a minimum version.
    • Authenticate the full negotiation transcript under keys the attacker cannot break; never fall back silently.
    • Plaintext-to-TLS upgrades must fail closed (implicit TLS, RFC 8314) or be pinned (HSTS).
    • Current TLS guidance: RFC 9325 (BCP 195).
    • TLS 1.3 defenses and why they are not enough alone
      • A 1.3 server that negotiates 1.2 writes DOWNGRD plus 0x01 into the last 8 bytes of ServerHello.random (0x00 for 1.1 or below). A 1.3 client seeing it aborts (RFC 8446 section 4.1.3).
        • TLS 1.2 (EC)DHE signs both randoms in ServerKeyExchange, so the sentinel cannot be stripped. Static RSA suites have no such signature.
      • The 1.3 transcript (CertificateVerify, Finished) covers ClientHello and ServerHello, so a 1.3 cipher cannot be changed in flight.
        • It does not cover a retry with a different ClientHello, nor a break of the weak crypto in real time.
      • TLS_FALLBACK_SCSV signals a deliberate fallback so a server can refuse it (RFC 7507).
  • Known attacks:
    • SSL 2.0 cipher suite rollback (1996, SSL 2.0): handshake messages were unauthenticated, so the attacker removed strong suites (Wagner and Schneier, USENIX Electronic Commerce 1996).
    • SSLstrip (2009, HTTP to HTTPS upgrade): an on-path attacker rewrites https links to http and proxies; HSTS (RFC 6797) fixes it (Marlinspike, Black Hat DC 2009).
    • POODLE (2014): downgrade dance to SSL 3.0; see Padding oracle (RFC 7568 deprecates SSL 3.0).
    • FREAK (2015, TLS export RSA): client state machines accepted an export RSA ServerKeyExchange in a non-export suite (CVE-2015-0204; Beurdouche et al., IEEE S&P 2015).
      • Servers reused one 512-bit export RSA key, which the attacker factored in hours.
    • Logjam (2015, TLS DHE_EXPORT): the attacker rewrites the suite to DHE_EXPORT; the 512-bit parameters are signed, the suite is not (Adrian et al., CCS 2015).
      • Precomputation made each discrete log take about a minute, and the export parameters pass as normal DHE.
    • DROWN (2016): SSLv2 on the same RSA key; see Key reuse across purposes.
    • SLOTH (2016, TLS 1.2, IKEv2, SSH): MD5 and SHA-1 transcript hashes allow transcript collisions for impersonation and downgrade (Bhargavan and Leurent, NDSS 2016).
    • Dragonblood (2019, WPA3-SAE): downgrade to WPA2 in transition mode, plus timing and cache leaks of the password (Vanhoef and Ronen, IEEE S&P 2020).
    • KNOB (2019, Bluetooth BR/EDR): unauthenticated key-length negotiation lowered session key entropy to 1 byte (Antonioli et al., USENIX Security 2019; CVE-2019-9506).
    • Terrapin (2023): strips SSH extension negotiation; see Truncation, reordering and dropped messages.
    • STARTTLS stripping: the attacker removes the upgrade offer from a plaintext SMTP or IMAP session (RFC 8314 discusses; HSTS, RFC 6797, fixes this for HTTP).
  • Sources
    • Beurdouche et al., IEEE S&P 2015; Adrian et al., CCS 2015; Bhargavan and Leurent, NDSS 2016; Antonioli et al., USENIX Security 2019.
    • RFC 7507; RFC 7568; RFC 8314; RFC 6797; RFC 8446 sections 4.1.3, 4.4.4; RFC 9325; OpenSSL SSL_CTX_set_min_proto_version(3).

Replay (protocol, freshness)

  • Root cause
    • A valid message is accepted twice. A MAC or signature over the body proves who sent it, not when, nor that it is the first time (RFC 8446 section 8 for the TLS case).
    • Servers keep no state, the state is per instance (so a replay hits another node), or the check is racy (check then insert); deployment patterns are our reasoning (uncertain).
  • Impact
    • Freshness breaks: the receiver cannot tell a first delivery from a copy, so an authentic old message runs again with its original authority.
      • Source: RFC 8446 section 8.
    • The attacker repeats a state-changing action without any key: a second payment, an unlock (RollJam), or a transaction on another chain (EIP-155).
    • Authenticity and integrity still hold: the attacker cannot change the message, only when and how often it takes effect.
  • Spot in C code
    • Request tag is HMAC(EVP_sha256(), key, .., body, ..) with no timestamp, nonce or sequence number in the MACed data.
    • Timestamp present but compared with a huge window, or the nonce cache is never pruned (memory growth) or pruned on a shorter interval than the window.
    • A lookup followed by a separate insert in a nonce table shared by threads without a lock, or a per-process table behind a load balancer.
    • Method, path, host or audience missing from the MACed data, so a signed request replays on another endpoint.
    • Session or JWT tokens with no exp, jti or audience (RFC 7519 section 4.1).
  • Design defense
    • MAC a timestamp plus a unique nonce or per-client counter, with method, path, host and query; reject stale and seen values.
      • Use an atomic insert in a shared store keyed by the nonce, with a TTL equal to the window.
    • Idempotency keys for state-changing calls limit duplicate effects.
    • Datagram protocols use a sliding anti-replay window over sequence numbers (RFC 6347 section 4.1.2.6; RFC 9147 for DTLS 1.3).
    • TLS 1.3 0-RTT data is replayable across connections (RFC 8446 section 8); servers need single-use tickets or ClientHello recording (sections 8.1 and 8.2).
      • Send only safe methods in early data; the server may answer 425 Too Early (RFC 8470).
      • OpenSSL: early data is opt-in on the server (SSL_CTX_set_max_early_data; SSL_CTX_set_max_early_data(3)); leave it off unless handlers are replay-safe.
    • AWS SigV4 signs a timestamp and rejects requests older than 5 minutes (AWS docs).
  • Known attacks:
    • RollJam (2015, rolling-code car key fobs): jam and record two codes, replay the first, keep the unused second for later (Kamkar, DEF CON 23 (uncertain)).
    • Ethereum fork replay (2016, Ethereum and Ethereum Classic): signed transactions had no chain id, so after the fork they were valid on both chains; EIP-155 adds it (EIP-155).
    • KRACK (2017): replays handshake message 3 to reset nonces; see Nonce and IV reuse.
    • TLS 1.3 0-RTT replay (2018, TLS 1.3 early data): early data can be replayed to the same or another server instance (RFC 8446 section 8).
  • Sources
    • RFC 6347 section 4.1.2.6; RFC 9147; RFC 8446 sections 8, 8.1, 8.2; RFC 8470; RFC 7519; AWS SigV4 docs; OpenSSL SSL_CTX_set_max_early_data(3).

Truncation, reordering and dropped messages (AEAD, integrity)

  • Root cause
    • Each chunk or message is authenticated alone, but nothing authenticates the sequence or the end.
      • The attacker drops the tail, swaps chunks or splices two streams, and every remaining piece verifies.
    • TLS close handling: an attacker injecting TCP FIN or RST truncates data unless the application requires a close_notify alert (RFC 8446 section 6.1).
  • Impact
    • Integrity of the whole stream breaks, though each AEAD chunk still verifies: the receiver accepts a message the sender never sent as a whole.
      • Source: Hoang et al., CRYPTO 2015; Bäumer et al., USENIX Security 2024.
    • The attacker cuts security-relevant tails (logout, Secure flag, SSH EXT_INFO) or reorders chunks to change meaning, with no key and no forged tag.
    • The receiver sees a valid but shorter or reordered message and treats it as complete (Smyth and Pironti, WOOT 2013).
  • Spot in C code
    • Chunked file or stream encryption with an independent random nonce per chunk and one EVP_aes_256_gcm() call per chunk with no chunk index or last flag.
    • Decrypt loops that end on EOF or a length field and treat that as success.
    • SSL_read returning 0 or an error treated as end of data without checking SSL_get_shutdown or SSL_ERROR_ZERO_RETURN (SSL_read(3)).
    • Length-prefixed frames whose length is outside the authenticated data.
  • Design defense
    • Use the STREAM construction: the nonce holds a chunk counter and a last-chunk flag, so truncation and reordering fail authentication (Hoang et al., CRYPTO 2015).
      • OpenSSL has no STREAM API: build the GCM nonce from a 64-bit chunk counter and a last-chunk byte; the reader requires the final chunk (our construction, uncertain).
      • age encrypts 64 KiB chunks this way (age specification).
    • Authenticate the total length or an end marker; require close_notify at the application layer.
    • Per-direction sequence numbers inside the MAC or nonce, as TLS does (RFC 8446 section 5.3).
  • Known attacks:
    • TLS truncation of logout (2013, HTTPS web apps): dropping the end of a logout exchange left the session alive while the user believed it closed (Smyth and Pironti, WOOT 2013).
    • Cookie Cutter (2014, HTTPS): truncating a response mid-header dropped the Secure flag from Set-Cookie (Bhargavan et al., IEEE S&P 2014).
    • Terrapin (2023, SSH): the attacker shifts sequence numbers during the handshake and drops EXT_INFO, downgrading extensions undetected.
      • Source: Bäumer, Brinkmann, Schwenk, "Terrapin Attack: Breaking SSH Channel Integrity By Sequence Number Manipulation", USENIX Security 2024; CVE-2023-48795.
  • Sources
    • Hoang et al., CRYPTO 2015; Smyth and Pironti, WOOT 2013; Bhargavan et al., IEEE S&P 2014; Bäumer et al., USENIX Security 2024.
    • RFC 8446 sections 5.3, 6.1; OpenSSL SSL_read(3); age specification.

Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)

  • Root cause
    • A valid ciphertext, tag or signature is accepted in a place it was not made for: another row, user, field, message type, protocol version or protocol.
      • Source: RFC 5116 section 2.1; Somorovsky et al., USENIX Security 2012.
    • Ambiguous encoding of concatenated fields (a || b equal for different splits) lets an attacker move bytes between fields (NIST SP 800-185 TupleHash exists to prevent this).
    • Hashes and signatures reused for several purposes with no label allow cross-protocol substitution (Mavrogiannopoulos et al., CCS 2012; Brinkmann et al., USENIX Security 2021).
  • Impact
    • Integrity of meaning breaks: the bytes are authentic, but the receiver applies them in a context the signer or encrypter never approved.
      • Source: RFC 5116 section 2.1; Somorovsky et al., USENIX Security 2012.
    • The attacker swaps another user's ciphertext into their own row, or reuses a signed blob as a different message type, without any key.
    • Results range from reading or claiming another user's data to SSO login as another user (SAML wrapping) or impersonating a server (CCS 2012).
  • Spot in C code
    • AEAD call with empty associated data on data that belongs to a user, row or message type.
    • OpenSSL GCM encryption with no EVP_EncryptUpdate(ctx, NULL, &len, aad, aad_len) call before the plaintext.
    • Hash or MAC input built with memcpy or snprintf of variable-length fields with no length prefix or separator.
    • Signing raw bytes with the same key for tokens, API requests and uploads.
    • HKDF (EVP_KDF HKDF, OSSL_KDF_PARAM_INFO) with an empty or constant info for different outputs (EVP_KDF-HKDF(7)).
  • Design defense
    • Put identifiers in the AEAD associated data (table, column, row id, key version); the receiver rebuilds it, it is not stored with the ciphertext (RFC 5116 sections 2.1 and 2.2).
    • Length-prefix or use a canonical, unambiguous encoding for every authenticated tuple.
    • Add a purpose label and version to every hash, MAC, signature and KDF call.
      • TLS 1.3 CertificateVerify signs 64 spaces, a context string and a zero byte before the transcript hash (RFC 8446 section 4.4.3).
    • The database-swap scenario is our reasoning from RFC 5116, not a cited incident (uncertain).
  • Known attacks:
    • STARTTLS command injection (2011, SMTP, IMAP, POP3): plaintext commands sent before STARTTLS were processed as if received over TLS (CVE-2011-0411).
    • SAML signature wrapping (2012, SAML single sign-on): the verifier checks the signature on one element while the app reads an injected one (Somorovsky et al., USENIX Security 2012).
    • TLS cross-protocol ServerKeyExchange (2012, TLS 1.2): signed ECDH parameters could be parsed by a client as DH parameters (Mavrogiannopoulos et al., CCS 2012).
    • ALPACA (2021, TLS across HTTPS, FTP, SMTP, IMAP, POP3): one certificate valid for several services lets an attacker redirect HTTPS to another protocol's server.
      • Source: Brinkmann et al., USENIX Security 2021.
  • Sources
    • RFC 5116 sections 2.1, 2.2; RFC 8446 section 4.4.3; NIST SP 800-185; CVE-2011-0411; OpenSSL EVP_KDF-HKDF(7).
    • Somorovsky et al., USENIX Security 2012; Mavrogiannopoulos et al., CCS 2012; Brinkmann et al., USENIX Security 2021.

Oracles and side channels

These attacks learn secrets one query at a time from errors, timing or length. Defense: one uniform error after authentication, constant-time code, no secrets mixed with attacker data.

Padding oracle (block cipher, confidentiality)

  • Root cause
    • A CBC decryptor reveals whether the padding is valid, by an error code, message or timing, before it authenticates the ciphertext.
    • CBC decryption is P_i = D_K(C_i) xor C_(i-1) (SP 800-38A section 6.2), so a byte flipped in C_(i-1) flips the same byte of P_i.
    • PKCS#7 padding appends n bytes of value n (1 to 16 for AES); the decryptor checks all n (RFC 5652 section 6.3; section uncertain).
    • The attacker changes bytes in the previous ciphertext block and watches the verdict.
      • A valid verdict means the last plaintext byte probably became 0x01, which reveals one byte of D_K(C_i); about 128 queries per byte.
    • The attack recovers plaintext (and, as CBC-R, can build chosen plaintext) but never the key (Vaudenay, EUROCRYPT 2002).
    • Variants: Lucky Thirteen read TLS CBC plaintext from MAC timing (AlFardan and Paterson, IEEE S&P 2013); POODLE used SSL 3.0 padding (2014); ASP.NET (Duong and Rizzo, IEEE S&P 2011).
  • Impact
    • Confidentiality breaks: the attacker decrypts any captured CBC ciphertext, about 128 queries per byte, without learning the key (Vaudenay, EUROCRYPT 2002).
    • POODLE used this to read HTTP session cookies from SSL 3.0 traffic, giving session hijack (CVE-2014-3566).
    • Integrity fails too: CBC-R builds ciphertexts that decrypt to chosen plaintext, such as forged ASP.NET auth tokens (Duong and Rizzo, IEEE S&P 2011).
  • Spot in C code
    • EVP_aes_*_cbc() decryption where EVP_DecryptFinal_ex failure (bad padding) is reported differently from a later MAC failure (EVP_DecryptInit(3)).
    • Encrypt-and-MAC or MAC-then-encrypt with CBC; a MAC check placed after the unpad step.
    • Distinct HTTP status, log line or response time for "bad padding" and "bad MAC".
    • Manual pad_len = buf[len-1] handling with early returns.
  • Design defense
    • Use an AEAD (AES-GCM, ChaCha20-Poly1305), which authenticates before releasing plaintext.
    • If CBC is unavoidable: encrypt-then-MAC, verify the MAC over IV and ciphertext in constant time first, and return one generic error (RFC 7366 for TLS).
    • Same error text, status and timing for every decryption failure.
  • Known attacks:
    • Vaudenay padding oracle (2002, CBC in SSL, IPsec, WTLS): a valid-padding verdict decrypts CBC byte by byte (Vaudenay, EUROCRYPT 2002).
    • Canvel et al. (2003, IMAP over TLS): timing told padding errors from MAC errors and recovered passwords (Canvel, Hiltgen, Vaudenay, Vuagnoux, CRYPTO 2003).
    • SSH CBC plaintext recovery (2009, SSH binary packet protocol): the encrypted length field was processed before the MAC check (Albrecht, Paterson, Watson, IEEE S&P 2009).
    • XML Encryption (2011, W3C XML Encryption CBC): parsing errors after decryption formed an oracle (Jager and Somorovsky, CCS 2011).
    • POODLE (2014, SSL 3.0 CBC): padding bytes are arbitrary and not MACed, so one byte leaks per about 256 requests (Moller, Duong, Kotowicz, 2014; CVE-2014-3566).
    • POODLE over TLS (2014, TLS stacks): implementations that skipped the TLS padding check (CVE-2014-8730).
    • Zombie POODLE and GOLDENDOODLE (2019, TLS CBC in appliances): observable padding checks in middleboxes (Young, 2019 (uncertain)).
  • Sources
    • Vaudenay 2002; RFC 7366; Bellare and Namprempre, ASIACRYPT 2000.

RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)

  • Root cause
    • An oracle tells the attacker whether a decrypted RSA ciphertext has valid PKCS#1 v1.5 padding.
      • RSA is malleable, so the attacker multiplies the ciphertext by s^e and narrows the plaintext interval from many queries (Bleichenbacher, CRYPTO 1998).
    • The oracle may be an error code, an alert, a timing difference or a connection reset.
    • ROBOT (2017) found it still present in major TLS stacks (USENIX Security 2018). Marvin (2023) is the timing variant (Kario; source not re-fetched, uncertain).
    • Signatures can also be forged under the same key if a decryption oracle exists (see key reuse).
  • Impact
    • Confidentiality breaks: the attacker decrypts a recorded RSA key-transport ciphertext, gets the TLS premaster secret and reads that session (Bleichenbacher, CRYPTO 1998).
    • The key is not recovered, but any recorded session under it can be decrypted, one oracle run each, since RSA key transport has no forward secrecy (RFC 8446 section 1.2).
    • The oracle computes private-key operations, so the attacker can also forge a signature under the same RSA key (Bock, Somorovsky, Young, USENIX Security 2018).
  • Spot in C code
    • RSA_private_decrypt(.., RSA_PKCS1_PADDING) or EVP_PKEY_CTX_set_rsa_padding(ctx, RSA_PKCS1_PADDING) on decrypt.
    • A TLS server or custom protocol that accepts RSA key transport.
    • Error paths that differ in message, status code or time for bad padding versus bad content (ERR_get_error codes returned to the peer).
  • Design defense
    • Do not use RSA encryption in new designs; use a KEM or HPKE (RFC 9180) and ECDHE.
    • If RSA is needed: RSA_PKCS1_OAEP_PADDING, with one undifferentiated error and no timing difference (RFC 8017 section 7.1; the OAEP decoding step must also be constant time).
    • TLS 1.3 removed RSA key transport (RFC 8446 section 1.2).
    • Implicit rejection: return a random fake plaintext instead of an error (RFC 5246 section 7.4.7.1 for TLS 1.2).
      • Recent OpenSSL versions add implicit rejection to PKCS#1 v1.5 decryption (version uncertain).
  • Known attacks:
    • Bleichenbacher 1998 (1998, SSL 3.0 RSA key exchange): a padding error distinct from other errors was an oracle; about a million queries recover the premaster secret (Bleichenbacher, CRYPTO 1998).
    • Klima-Pokorny-Rosa (2003, TLS RSA key exchange): the premaster version-number check became a new oracle (Klima, Pokorny, Rosa, CHES 2003).
    • DROWN (2016): SSLv2 Bleichenbacher oracle used on TLS; see Key reuse across purposes.
    • ROBOT (2017, TLS RSA key exchange): the 1998 oracle was still present in major TLS stacks and appliances (Bock, Somorovsky, Young, USENIX Security 2018).
    • Nine lives of Bleichenbacher's CAT (2019, TLS RSA key exchange): cache side channels revived the oracle in patched libraries (Ronen et al., IEEE S&P 2019).
  • Sources
    • Bleichenbacher, CRYPTO 1998; Bock, Somorovsky, Young, USENIX Security 2018; RFC 8017 section 7.1; RFC 8446 section 1.2.

Timing side channels (MAC, confidentiality, integrity)

  • Root cause
    • Execution time, memory access pattern or branches depend on secret data, so an observer infers the secret from measured time.
    • Early-exit comparison: memcmp and strcmp may return at the first differing byte, so response time grows with the length of the matching prefix.
      • An attacker recovers a MAC tag byte by byte, about 256 * tag_len guesses times the samples needed, instead of 2^(8 * tag_len).
    • Remote timing is measurable with enough samples (Brumley and Boneh, USENIX Security 2003; Crosby et al. 2009).
    • Other sources: secret-indexed table lookups (table-based AES leaks through cache timing; Bernstein 2005), secret-dependent branches, variable-time big-integer code (Marvin).
  • Impact
    • Integrity breaks: the attacker learns a valid MAC tag for its own forged message byte by byte, so the verifier accepts data the key holder never authenticated (uncertain).
    • Confidentiality breaks: secret-dependent timing leaks key bits; Bernstein recovered a full AES key from a remote server via cache timing (Bernstein 2005).
    • Brumley and Boneh extracted an OpenSSL RSA private key over a network (USENIX Security 2003); Raccoon leaks the DH secret to decrypt a session (Merget et al., 2021).
  • Spot in C code
    • memcmp(computed, received, n) == 0, strcmp or strncmp on MACs, tokens, password hashes or API keys; also hex or base64 strings compared this way.
    • Hand-written loops with break or return on the first mismatch.
    • if (secret_bit) { .. }, table[secret_byte], % or / on secrets in hand-written code.
    • Hand-written crypto in place of audited libraries; ladder or table code with branches on key bits.
int check(const uint8_t key[32], const uint8_t *msg, size_t n,
          const uint8_t tag[32]) {
    uint8_t mac[32];
    unsigned int len = sizeof mac;
    HMAC(EVP_sha256(), key, 32, msg, n, mac, &len);
    /* Constant time: CRYPTO_memcmp, not memcmp. */
    return CRYPTO_memcmp(mac, tag, 32) == 0;
}
  • Design defense
    • OpenSSL CRYPTO_memcmp(3) (constant time, equality only) after checking lengths, which are public.
    • Use library implementations built for constant-time execution (AES-NI or bitsliced AES, ChaCha20, OpenSSL X25519).
    • Compilers can undo constant-time source; check the generated code or use tools such as dudect (uncertain).
    • Avoid secret-dependent timing in error paths: same work and same response for every failure.
  • Known attacks:
    • Lucky13 (2013, TLS and DTLS CBC): the MAC runs over a padding-dependent length, so MAC timing leaks padding (AlFardan and Paterson, IEEE S&P 2013).
    • Raccoon (2020, TLS 1.2 and earlier DH(E)): leading zero bytes of the DH secret are stripped before the KDF, so timing leaks a zero top byte (Merget et al., USENIX Security 2021).
  • Sources
    • OpenSSL CRYPTO_memcmp(3); Brumley and Boneh 2003; Bernstein, "Cache-timing attacks on AES", 2005.

Compression oracles (CRIME and BREACH) (protocol, confidentiality)

  • Root cause
    • Compression makes length depend on content, and encryption preserves length.
      • When attacker-chosen data is compressed together with a secret, a guess matching the secret compresses better and the ciphertext shrinks.
    • The attacker repeats the guess byte by byte and recovers cookies or tokens; it leaks secrets in the plaintext, not keys.
    • CRIME (2012) used TLS-level compression; TLS 1.3 removed it (legacy_compression_methods must be the single null method, RFC 8446 section 4.1.2).
    • BREACH (2013) uses HTTP body gzip, so TLS 1.3 does not help when a response holds a secret and reflected input (Gluck, Harris, Prado, Black Hat 2013).
  • Impact
    • Confidentiality breaks for secrets in the plaintext: the attacker recovers a session cookie or CSRF token from ciphertext lengths alone (CVE-2012-4929; Gluck, Harris, Prado 2013).
    • A stolen cookie gives session hijack; a stolen CSRF token lets the attacker forge requests as the user (our reasoning, uncertain).
    • The key and other traffic stay safe: encryption hides content, not length, so only secrets compressed with attacker data leak (RFC 7457 section 2.6).
  • Spot in C code
    • zlib deflate or compress2 (or zstd, brotli) followed by encryption of a message that mixes a secret with attacker-influenced data.
    • OpenSSL builds with TLS compression enabled (SSL_OP_NO_COMPRESSION not set on old versions).
    • HTTP responses with gzip or brotli enabled that echo input next to a CSRF token or session secret.
    • Messages whose compressed length reaches an observer, such as on a network trace.
  • Design defense
    • Do not compress messages that carry secrets, or compress secrets and attacker data in separate contexts.
    • Per-request masked CSRF tokens (random mask each response), SameSite cookies and rate limits against repeated guesses.
    • Pad lengths only as defense in depth (it raises cost, not a fix; uncertain).
  • Known attacks:
    • VoIP VBR phrase spotting (2008, SRTP with VBR codecs): packet lengths of encrypted calls revealed spoken phrases (Wright et al., IEEE S&P 2008).
    • CRIME (2012, TLS and SPDY compression): compressed request headers leaked cookies by length (Rizzo and Duong, Ekoparty 2012; CVE-2012-4929).
    • BREACH (2013, HTTP gzip responses): compressed response bodies leaked CSRF tokens by length (Gluck, Harris, Prado, Black Hat USA 2013).
    • TIME (2013, HTTP responses): browser-side timing measured compressed size, no network tap needed (Be'ery and Shulman, Black Hat Europe 2013).
    • HEIST (2016, HTTPS via browser APIs): browser timing APIs measured response sizes from JavaScript (Vanhoef and Van Goethem, Black Hat USA 2016).
  • Sources
    • Rizzo and Duong, "The CRIME Attack", Ekoparty 2012; RFC 7457 section 2.6; RFC 8446 section 4.1.2.

Primitive misuse

These attacks use a sound primitive outside its contract: repeated nonces, no MAC, raw hash as MAC, bad randomness, shared keys, unchecked points. Defense: misuse-resistant APIs and checks.

Nonce and IV reuse (AEAD, confidentiality, integrity)

  • Root cause
    • A stream-cipher-based AEAD (AES-GCM, ChaCha20-Poly1305) derives its keystream from key and nonce, so a repeated nonce repeats the keystream.
    • Confidentiality: C1 xor C2 = P1 xor P2; a known or guessable P1 reveals P2.
    • Integrity (GCM): two tags under one nonce let the attacker solve for the GHASH key H = E_K(0^128) and forge tags for chosen ciphertexts (Joux's forbidden attack).
      • H is not the master key K, so other nonces stay confidential, but forgery works for any nonce under which the attacker has seen one valid tag.
      • Tag: T = GHASH_H(A, C) xor E_K(J0), J0 from the nonce; a repeated nonce cancels E_K(J0) in T1 xor T2, leaving a polynomial in H (SP 800-38D sections 6.4, 7.1).
      • ChaCha20-Poly1305: a reused nonce reuses the Poly1305 one-time key, which also allows forgery.
    • Random 96-bit nonces collide by the birthday bound: NIST caps a key at 2^32 random-nonce messages (SP 800-38D section 8.3).
      • With q random 96-bit nonces, collision probability is about q^2 / 2^97; at q = 2^32 that is 2^-33, under the 2^-32 target (target from SP 800-38D section 8, uncertain).
    • Real cases: TLS servers repeating GCM nonces (Boeck et al., WOOT 2016); WPA2 KRACK reset the nonce by replaying a handshake message (Vanhoef and Piessens, CCS 2017).
  • Impact
    • Confidentiality: the attacker learns P1 xor P2 and recovers any message encrypted under a reused nonce with a known or guessable one (SP 800-38D section 8).
    • Integrity: with GCM's H recovered, the attacker forges valid tags on chosen ciphertexts, which the receiver accepts as authentic (Joux 2006).
      • The forgery capability lasts until the key rotates, since H depends only on the key (SP 800-38D section 6.4).
  • Spot in C code
    • uint8_t nonce[12] = {0}; or a string-literal nonce passed to EVP_EncryptInit_ex.
    • Nonce derived from a message field or a low-resolution timestamp (time(NULL)).
    • Counter nonce in a static variable only (restart, crash recovery or a restored VM snapshot resets it), or per-process counters when several processes or nodes share a key.
    • Both directions starting from counter zero with the same key (see reflection).
    • Random 96-bit nonces (RAND_bytes(nonce, 12)) on a key that encrypts more than about 2^32 messages.
    • Retry paths that re-encrypt a modified message under the same nonce.
int seal(EVP_CIPHER_CTX *ctx, const unsigned char key[32],
         const unsigned char *m, int mlen, unsigned char *c) {
    /* Finding: fixed nonce, every call reuses the keystream. */
    static const unsigned char iv[12] = {0};
    int len;
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, key, iv);
    return EVP_EncryptUpdate(ctx, c, &len, m, mlen);
}
  • Design defense
    • Persisted or per-sender counter nonces with sender id in the nonce; TLS 1.3 XORs a per-direction static IV with the record sequence number (RFC 8446 section 5.3).
    • XChaCha20-Poly1305: 192-bit nonces make random nonces safe for practical volumes (draft-irtf-cfrg-xchacha); not an OpenSSL EVP cipher (uncertain).
    • AES-GCM-SIV (RFC 8452): the tag is the CTR IV, so reuse only leaks equality of (nonce, AD, plaintext). It needs two passes, so it cannot stream.
    • Rotate keys by message count; derive per-message keys with HKDF.
  • Known attacks:
    • WEP (2001, 802.11 WEP): 24-bit IVs repeat keystreams, and RC4 with the IV prefixed to the key leaks the key (Fluhrer, Mantin, Shamir, SAC 2001).
    • BEAST (2011, TLS 1.0 CBC): the next record's IV was the last ciphertext block, so it was predictable, enabling byte-at-a-time cookie recovery (Duong and Rizzo, Ekoparty 2011; CVE-2011-3389).
    • Nonce-disrespecting adversaries (2016, TLS AES-GCM): servers repeated or randomly collided GCM nonces, allowing forgery (Bock et al., WOOT 2016).
    • SWEET32 (2016, TLS and OpenVPN with 3DES or Blowfish): 64-bit blocks collide after about 2^32 blocks in CBC, revealing plaintext XORs (Bhargavan and Leurent, CCS 2016; CVE-2016-2183).
    • KRACK (2017, WPA2 four-way handshake): replaying handshake message 3 reinstalls the key and resets the nonce (Vanhoef and Piessens, CCS 2017; CVE-2017-13077).
  • Sources
    • NIST SP 800-38D sections 7 and 8.3; Joux 2006 comment to NIST; RFC 8439; RFC 8452.

ECB and unauthenticated encryption (block cipher, confidentiality, integrity)

  • Root cause
    • ECB encrypts each 16-byte block independently, so equal plaintext blocks give equal ciphertext blocks and structure leaks (SP 800-38A section 6.1).
      • With an attacker-controlled prefix it also allows byte-at-a-time recovery of an appended secret (Cryptopals; uncertain as a source).
    • Unauthenticated CTR (and stream ciphers): C = P xor keystream, so flipping bit i of C flips bit i of P with no error.
      • With a known field, the attacker XORs in known xor wanted to rewrite role=user into role=root.
    • Unauthenticated CBC: flipping a bit in C_(i-1) flips the same bit in P_i and garbles P_(i-1). EFAIL (2018) used CBC and CFB malleability in S/MIME and OpenPGP mail.
    • MAC order: encrypt-then-MAC lets the receiver reject tampering before decrypting, so there is no decryption oracle.
      • MAC-then-encrypt with CBC must decrypt and unpad first (padding oracle). Encrypt-and-MAC with a deterministic MAC leaks equal plaintexts.
  • Impact
    • Confidentiality: ECB shows which plaintext blocks are equal and, with a chosen prefix, leaks an appended secret byte by byte (SP 800-38A section 6.1).
    • Integrity: without a MAC the attacker rewrites fields (role=user to role=root) or splices blocks, and the receiver accepts the result as genuine (SP 800-38A appendix D; uncertain).
      • Malleability can also break confidentiality: EFAIL modified ciphertexts so the mail client sent the plaintext to the attacker (Poddebniak et al., USENIX Security 2018).
  • Spot in C code
    • EVP_aes_*_ecb(), AES_ecb_encrypt or AES_encrypt called per block in a loop.
    • EVP_aes_*_ctr(), _cbc() or _cfb() with no MAC step, or a MAC computed over plaintext only.
    • GCM decrypt where the EVP_CTRL_AEAD_SET_TAG / EVP_DecryptFinal_ex result is ignored, so unverified plaintext is used (EVP_EncryptInit(3)).
    • Tag over the ciphertext but not the IV, nonce or associated data.
    • Encrypted cookies or tokens decoded and trusted without authentication.
  • Design defense
    • Use an AEAD, which authenticates the ciphertext before releasing plaintext (RFC 5116): OpenSSL EVP_aes_256_gcm() or EVP_chacha20_poly1305() with AAD set via EVP_EncryptUpdate(ctx, NULL, ..).
    • If composing by hand: encrypt-then-MAC over IV, ciphertext and AD with an independent MAC key (Bellare and Namprempre 2000).
    • Release no plaintext until the tag check returns success.
  • Known attacks:
    • WEP bit flipping (2001, 802.11 WEP): CRC-32 is linear and the cipher a stream, so bits flip and the checksum is fixed up (Borisov, Goldberg, Wagner, MobiCom 2001).
    • iMessage (2016, Apple iMessage): unauthenticated AES-CTR let an attacker modify and re-sign ciphertexts to decrypt attachments (Garman et al., USENIX Security 2016).
    • EFAIL (2018, S/MIME and OpenPGP): CBC and CFB malleability injected exfiltration links into encrypted mail (Poddebniak et al., USENIX Security 2018).
  • Sources
    • NIST SP 800-38A sections 6.1 and 6.5; EFAIL, USENIX Security 2018.

Hash length extension (hash/MAC, integrity)

  • Root cause
    • A Merkle-Damgard hash (MD5, SHA-1, SHA-256, SHA-512) outputs its full internal state, so H(m) is a valid starting state for hashing more data.
    • With tag = H(secret || m), the attacker knows tag, m and the length of secret.
      • It sets the hash state to tag and keeps hashing ext, producing a valid tag for secret || m || pad || ext without the secret.
    • It is a forgery; the secret stays unknown. Real case: Flickr API signatures MD5(secret || params) (Duong and Rizzo, 2009).
    • Why the glue padding is needed
      • The hash only releases its state after the padded message was processed: secret || m || 0x80 || zeros || 64-bit bit length.
        • The padded input is a whole number of blocks (64 bytes for SHA-256; FIPS 180-4 section 5.1.1).
      • The forged message must start with exactly those bytes, so the old padding becomes part of the message. This is the glue padding, and the verifier recomputes the same total.
    • Why the attacker needs the secret length
      • The glue padding contains the bit length of secret || m, and the new padding at the end contains the total length including secret, so both depend on it.
      • The length is guessed by trying plausible values (often 8 to 64 bytes); a wrong guess yields an invalid tag.
  • Impact
    • Integrity: the attacker forges a valid tag for m || pad || ext, so the server accepts appended parameters or commands as authenticated (Duong and Rizzo, 2009).
    • The secret stays unknown, but H(secret || m) is not unforgeable, so it fails as a MAC; HMAC exists to fix this (RFC 2104, uncertain as the motivating source).
  • Spot in C code
    • SHA256_Init, SHA256_Update(&c, secret, ..), SHA256_Update(&c, msg, ..), SHA256_Final used as authentication.
    • EVP_Digest over a buffer built as secret || msg, compared with a client-supplied value.
    • Home-made H(key || data), H(data || key) (still weak against collisions) or H(key || data || key) constructions.
    • Plain SHA-2 calls where a keyed primitive (HMAC or EVP_MAC_fetch(NULL, "HMAC", NULL)) is needed.
  • Design defense
    • HMAC (RFC 2104): the outer hash hides the inner state.
    • SHA-3 and KMAC are sponges: the output exposes only the rate part, and the hidden capacity (512 bits for SHA3-256) would have to be guessed to resume the state (FIPS 202).
      • If the capacity leaked, the attacker could continue absorbing as if it knew the state, so it is the part that carries security.
    • Keyed BLAKE2 (OpenSSL 3 BLAKE2BMAC, EVP_MAC-BLAKE2(7)) or BLAKE3; KMAC (EVP_MAC-KMAC(7)); truncated SHA-2 (SHA-384, SHA-512/256) hides part of the state.
  • Known attacks:
    • Rogue CA (related, collision) (2008, X.509 with MD5): an MD5 chosen-prefix collision turned a site certificate into a CA certificate (Stevens et al., CRYPTO 2009).
    • Flickr API signature forgery (2009, Flickr API): MD5(secret || params) signatures were extended with new parameters (Duong and Rizzo, 2009).
    • SHA-1 is a Shambles (related, collision) (2020, PGP web of trust): a SHA-1 chosen-prefix collision forged key certifications (Leurent and Peyrin, USENIX Security 2020).
  • Sources
    • FIPS 180-4; RFC 2104; FIPS 202; Duong and Rizzo, "Flickr's API Signature Forgery Vulnerability", 2009.

Weak or misused RNG (RNG, confidentiality)

  • Root cause
    • Keys, nonces or signature randomness come from a predictable, low-entropy or duplicated source, so an attacker enumerates or recomputes them.
    • Low boot entropy: headless devices generated RSA keys at first boot before the Linux pool was seeded, and many drew the same first prime.
      • Two moduli sharing a prime fall to gcd(N1, N2) = p, then q = N1 / p; this factored about 0.5% of TLS hosts' keys (Heninger et al., USENIX Security 2012).
      • Batch GCD scales it: a product tree gives P = N1 * .. * Nk, a remainder tree gives z_i = P mod N_i^2, and gcd(N_i, z_i / N_i) exposes shared primes (Heninger et al. 2012).
    • Debian OpenSSL (2006 to 2008) generated keys from a tiny seed space of process ids (CVE-2008-0166; detail from memory).
    • ECDSA: a repeated k gives k = (z1 - z2) / (s1 - s2) mod n then d = (s1 k - z1) / r mod n. A biased k falls to lattice attacks (hidden number problem).
      • Real cases: Sony PS3 constant k (fail0verflow, 2010); Android SecureRandom bug, 2013; Minerva and TPM-Fail, 2020.
  • Impact
    • Confidentiality: the attacker recomputes or enumerates the keys, then decrypts traffic and data protected by them (Heninger et al., USENIX Security 2012).
      • Shared primes factor RSA moduli outright; Debian OpenSSL keys could be precomputed from the small seed space (CVE-2008-0166).
    • A repeated or biased ECDSA k leaks the signing key d, so the attacker also forges signatures (fail0verflow, 2010).
  • Spot in C code
    • rand(), random(), drand48() or srand(time(NULL)) anywhere near keys, nonces, tokens or salts.
    • RAND_bytes return value ignored (it returns 1 on success; RAND_bytes(3)), or the deprecated RAND_pseudo_bytes.
    • Reading /dev/urandom without checking the read length, or key generation at first boot before the OS pool is seeded (getrandom(2) with no flags blocks until initialized).
    • A DRBG state copied by fork or a VM snapshot without reseeding.
    • Hand-rolled ECDSA with an RNG k, or a custom RNG callback.
  • Design defense
    • Long-term keys from getrandom(2), arc4random_buf, OpenSSL RAND_bytes (checked).
    • RFC 6979 (deterministic ECDSA) and Ed25519 (RFC 8032 section 5.1.6; OpenSSL EVP_DigestSign with an Ed25519 key) remove the RNG from signing.
      • Fault attacks on deterministic signing are a known caveat; hedged variants exist (uncertain).
    • Block key generation until the OS RNG is seeded; reseed after fork or snapshot.
  • Sources
    • Heninger et al. 2012; RFC 6979; RFC 8032; OpenSSL RAND_bytes(3).

Key reuse across purposes (KDF, integrity)

  • Root cause
    • One key serves two purposes or two protocols, so an oracle in one becomes an attack on the other. Security proofs assume independent keys, and NIST SP 800-57 says one key, one purpose.
    • RSA: textbook decryption c^d and signing m^d are the same operation, so a decryption oracle is a signing oracle.
      • With PKCS#1 v1.5, a Bleichenbacher oracle can forge signatures under the same key (Jager et al., CCS 2015).
    • DROWN (2016): one RSA key in SSLv2 and TLS let the SSLv2 oracle decrypt TLS sessions.
    • CBC-MAC under the CBC encryption key is forgeable: with a zero IV the last ciphertext block equals the tag, so an encryption oracle is a MAC oracle (textbook result; primary source uncertain).
    • One key for both directions or in test and production widens the blast radius and creates nonce collisions.
  • Impact
    • Integrity: an oracle in one use forges in another; a decryption oracle on an RSA key signs attacker messages, so peers accept forged handshakes (Jager et al., CCS 2015).
    • Confidentiality also falls: DROWN used SSLv2 to decrypt recorded TLS sessions under the shared key (Aviram et al., USENIX Security 2016).
  • Spot in C code
    • The same key buffer passed to both an encryption call and HMAC() or a signing call.
    • One key loaded from one config field and used for several features.
    • The same RSA EVP_PKEY used for both OAEP decryption and signing.
    • HKDF (EVP_KDF HKDF) with the same info for different outputs.
  • Design defense
    • Derive one key per purpose and direction with HKDF-Expand and distinct info labels (RFC 5869; OpenSSL EVP_KDF-HKDF(7)), or generate independent keys.
    • Separate keys per environment, tenant and protocol version; track key purpose in metadata.
  • Known attacks:
    • EMV joint security (2012, EMV payment cards): one RSA key for signing and encryption enabled signature forgery (Degabriele et al., CT-RSA 2012).
    • TLS 1.3 and QUIC signature forgery (2015, TLS 1.3 drafts and QUIC): a PKCS#1 v1.5 decryption oracle on the same RSA key forged signatures (Jager, Schwenk, Somorovsky, CCS 2015).
    • DROWN (2016, SSLv2 and TLS sharing an RSA key): an SSLv2 Bleichenbacher oracle decrypted TLS sessions (Aviram et al., USENIX Security 2016; CVE-2016-0800).
    • IKE key reuse (2018, IPsec IKEv1 and IKEv2): one RSA key across modes let a Bleichenbacher oracle in one mode break the others (Felsch et al., USENIX Security 2018).
  • Sources
    • NIST SP 800-57 Part 1 Rev 5 section 5.2; Jager, Schwenk, Somorovsky, CCS 2015; DROWN, USENIX Security 2016.

Invalid curve and small subgroup (KEM/DH, confidentiality)

  • Root cause
    • Short Weierstrass addition and doubling use a but never b, so an off-curve point (x, y) lies on another curve y^2 = x^3 + ax + b' and the server computes there.
    • The attacker picks b' with a point Q of small prime order q; d * Q lies in a subgroup of size q, and any response that depends on the shared secret reveals d mod q.
      • Repeat for many small primes and combine residues with the CRT to get d; this needs a reused static key.
      • With x-only shared secrets each residue is known only up to sign; more queries resolve it.
    • Real case: Jager, Schwenk, Somorovsky (ESORICS 2015) recovered keys from TLS-ECDH implementations.
    • Finite-field DH has the same shape: a peer value of small order (1, p-1) or outside the prime-order subgroup leaks key bits; Logjam also showed weak shared groups.
  • Impact
    • Confidentiality: the attacker recovers the static private key d, derives every shared secret made with it, and decrypts those sessions (Jager et al., ESORICS 2015).
      • In static ECDH the same key authenticates the server, so the attacker can also impersonate it (uncertain).
  • Spot in C code
    • Hand-rolled ECC (bignum arithmetic) that parses (x, y) without an on-curve test.
    • OpenSSL: EC_POINT_set_affine_coordinates or EC_POINT_oct2point results used with no EC_POINT_is_on_curve, EC_KEY_check_key or EVP_PKEY_public_check.
      • Source: OpenSSL man pages; which calls check the curve equation differs by version (uncertain).
    • OpenSSL DH: peer value not checked with DH_check_pub_key or EVP_PKEY_public_check.
    • A reused static ECDH key answering many requests, instead of ephemeral keys.
    • X25519 via OpenSSL EVP_PKEY_derive with its return value ignored; OpenSSL fails the derive on an all-zero output (uncertain).
  • Design defense
    • Validate public keys: not the identity, coordinates in range, on the curve, correct order (NIST SP 800-56A Rev 3 section 5.6.2.3).
      • P-256 has cofactor 1, so on-curve implies correct order.
    • Prefer ephemeral keys, so leaked residues cannot be combined.
    • X25519: an x-only Montgomery ladder; every 32-byte input is on the curve or its secure twist, and clamping clears the low 3 bits (cofactor 8). RFC 7748 allows aborting on an all-zero output.
    • Compressed points cannot encode an off-curve point because decoding solves for y.
    • Finite-field DH: use RFC 7919 named groups and check the peer value is in range 1 < y < p-1.
    • Ed25519 verification: reject small-order keys and R; check what the library rejects (OpenSSL behavior uncertain).
  • Known attacks:
    • Lim-Lee small subgroup (1997, DH-based protocols): peer values in small subgroups leak the static key modulo small primes (Lim and Lee, CRYPTO 1997).
    • Invalid curve attack (2000, elliptic curve protocols): off-curve points move the computation to a weak curve (Biehl, Meyer, Muller, CRYPTO 2000).
    • TLS-ECDH invalid curve (2015, Java and other TLS-ECDH stacks): static ECDH keys were recovered from unvalidated points (Jager, Schwenk, Somorovsky, ESORICS 2015).
    • Measuring small subgroup attacks (2017, TLS, IPsec, SSH DH): many servers used non-safe groups without subgroup checks (Valenta et al., NDSS 2017).
    • Monero key image (2017, CryptoNote Ed25519): cofactor-8 key images allowed double spends (Monero disclosure, 2017 (uncertain)).
    • Bluetooth fixed coordinate (2018, Bluetooth pairing): only the x coordinate was authenticated and y was not validated (Biham and Neumann, SAC 2019; CVE-2018-5383).
  • Sources
    • SP 800-56A Rev 3 section 5.6.2.3; RFC 7748 sections 5, 6.1, 7; Jager et al. 2015.

Token and format

These attacks let the untrusted token pick the algorithm or key it is verified with. Defense: pin the algorithm and key per use in configuration and ignore header hints.

JWT algorithm confusion (signature, auth)

  • Root cause
    • The verifier takes the algorithm (or the key) from the untrusted token header.
    • alg: none: a verifier that honors it accepts an unsigned token.
    • Key confusion: the server holds an RSA public key and expects RS256; the attacker sets alg: HS256 and MACs the token with the public key bytes as the HMAC secret.
      • A verifier that follows alg accepts it (McLean, Auth0 blog, 2015).
    • Header-driven key lookup is a related attack: jku, x5u, jwk or a kid used in a file path or SQL query.
    • alg names signature or MAC algorithms, not ciphers.
  • Impact
    • Authentication: the attacker mints tokens with any claims (sub, role), so it acts as any user or admin without the signing key (RFC 8725 section 2.1).
      • Key confusion needs only the public key, which is published, so anyone can forge (McLean, Auth0 blog, 2015).
    • Header-driven key lookup lets the attacker supply its own key, or inject SQL or a path through kid (RFC 8725 section 3.10, uncertain).
  • Spot in C code
    • A hand-written or library verify path that reads alg from the parsed header and dispatches on it (strcmp(alg, "HS256")).
    • A public-key PEM loaded as a byte string and passed as an HMAC key.
    • libjwt: the expected algorithm not passed to the verifier, or jwt_get_alg not compared to it after decode (API differs by libjwt version; uncertain).
    • exp, aud and iss not validated; header kid interpolated into a query or path.
/* Stubs so the fence compiles; the app defines these. */
typedef struct { const unsigned char *bytes; size_t len; } jwt_key;
typedef struct { char alg[16]; } jwt_hdr;
int parse_header(const char *tok, jwt_hdr *h);
int hmac_verify(const char *tok, const unsigned char *k, size_t n);
int rsa_verify(const char *tok, const jwt_key *key);

int verify_token(const char *tok, const jwt_key *key) {
    jwt_hdr h;
    parse_header(tok, &h);
    /* Finding: algorithm chosen by the token. */
    if (strcmp(h.alg, "HS256") == 0)
        return hmac_verify(tok, key->bytes, key->len);
    return rsa_verify(tok, key);
}
  • Design defense
    • Pin one algorithm per key and ignore the header's choice (RFC 8725 sections 3.1 and 3.2); reject any token whose alg differs.
      • Keys come from configuration or an allowlisted JWKS, never from the token.
    • Validate exp, aud and iss (RFC 8725, section numbers uncertain).
    • Reject none unconditionally.
    • Use asymmetric signatures when verifiers must not mint tokens.
  • Sources
    • RFC 8725; McLean 2015; libjwt docs.
