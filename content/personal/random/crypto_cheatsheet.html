Crypto and security review cheatsheet

Quick-reference notes for a crypto and security review interview: primitives, attacks, and how to review architectures and code for vulnerabilities.

Primitives

Attacks

Protocol attacks come first, with the most depth; primitive-level attacks follow. Each section gives root cause, how to spot it in C code, and the design defense. Sources are named inline; items marked uncertain were not re-fetched.

Named protocol attacks index

One entry per named attack, pointing to the category and attack where its Known attacks: entry lives.

  • Lowe's attack on Needham-Schroeder (1995, Needham-Schroeder public key): see Authentication and key exchange > Unknown key share and missing identity binding (KEM/DH, auth)
    • message 2 omits B's identity, so an insider relays A's run and B believes it talks to A.
  • SSL 2.0 cipher suite rollback (1996, SSL 2.0): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • handshake messages were unauthenticated, so the attacker removed strong suites.
  • Lim-Lee small subgroup (1997, DH-based protocols): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • peer values in small subgroups leak the static key modulo small primes.
  • Bleichenbacher 1998 (1998, SSL 3.0 RSA key exchange): see Oracles and side channels > RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)
    • a padding error distinct from other errors was an oracle; about a million queries recover the premaster secret.
  • STS unknown key share (1999, station-to-station): see Authentication and key exchange > Unknown key share and missing identity binding (KEM/DH, auth)
    • the attacker certifies the victim's public key under its own name.
  • Invalid curve attack (2000, elliptic curve protocols): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • off-curve points move the computation to a weak curve.
  • MQV unknown key share (2001, MQV key agreement): see Authentication and key exchange > Unknown key share and missing identity binding (KEM/DH, auth)
    • an online UKS attack on the protocol as specified.
  • SMBRelay (2001, NTLM over SMB): see Authentication and key exchange > Missing channel binding (protocol, auth)
    • an NTLM exchange is relayed to another server; Extended Protection later added channel binding.
  • WEP (2001, 802.11 WEP): see Primitive misuse > Nonce and IV reuse (AEAD, confidentiality, integrity)
    • 24-bit IVs repeat keystreams, and RC4 with the IV prefixed to the key leaks the key.
  • WEP bit flipping (2001, 802.11 WEP): see Primitive misuse > ECB and unauthenticated encryption (block cipher, confidentiality, integrity)
    • CRC-32 is linear and the cipher a stream, so bits flip and the checksum is fixed up.
  • Vaudenay padding oracle (2002, CBC in SSL, IPsec, WTLS): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • a valid-padding verdict decrypts CBC byte by byte.
  • Canvel et al. (2003, IMAP over TLS): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • timing told padding errors from MAC errors and recovered passwords.
  • Klima-Pokorny-Rosa (2003, TLS RSA key exchange): see Oracles and side channels > RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)
    • the premaster version-number check became a new oracle.
  • Tunneled authentication MITM (2003, PEAP and other EAP tunnels): see Authentication and key exchange > Missing channel binding (protocol, auth)
    • inner credentials not bound to the outer TLS tunnel are relayed into another tunnel.
  • Rogue CA (related, collision) (2008, X.509 with MD5): see Primitive misuse > Hash length extension (hash/MAC, integrity)
    • an MD5 chosen-prefix collision turned a site certificate into a CA certificate.
  • SMB NTLM reflection (2008, Windows SMB): see Authentication and key exchange > Reflection (MAC, auth)
    • the attacker returned a victim's NTLM challenge-response to the victim's own SMB server.
  • VoIP VBR phrase spotting (2008, SRTP with VBR codecs): see Oracles and side channels > Compression oracles (CRIME and BREACH) (protocol, confidentiality)
    • packet lengths of encrypted calls revealed spoken phrases.
  • Flickr API signature forgery (2009, Flickr API): see Primitive misuse > Hash length extension (hash/MAC, integrity)
    • MD5(secret || params) signatures were extended with new parameters.
  • SSH CBC plaintext recovery (2009, SSH binary packet protocol): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • the encrypted length field was processed before the MAC check.
  • SSLstrip (2009, HTTP to HTTPS upgrade): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • an on-path attacker rewrites https links to http and proxies; HSTS (RFC 6797) fixes it.
  • TLS renegotiation attack (2009, TLS up to 1.2): see Authentication and key exchange > Missing channel binding (protocol, auth)
    • the attacker sends a prefix, then the victim's handshake renegotiates the same connection and the server joins both; fixed by RFC 5746.
  • BEAST (2011, TLS 1.0 CBC): see Primitive misuse > Nonce and IV reuse (AEAD, confidentiality, integrity)
    • the next record's IV was the last ciphertext block, so it was predictable, enabling byte-at-a-time cookie recovery.
  • STARTTLS command injection (2011, SMTP, IMAP, POP3): see Negotiation and message state > Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)
    • plaintext commands sent before STARTTLS were processed as if received over TLS.
  • XML Encryption (2011, W3C XML Encryption CBC): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • parsing errors after decryption formed an oracle.
  • CRIME (2012, TLS and SPDY compression): see Oracles and side channels > Compression oracles (CRIME and BREACH) (protocol, confidentiality)
    • compressed request headers leaked cookies by length.
  • EMV joint security (2012, EMV payment cards): see Primitive misuse > Key reuse across purposes (KDF, integrity)
    • one RSA key for signing and encryption enabled signature forgery.
  • SAML signature wrapping (2012, SAML single sign-on): see Negotiation and message state > Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)
    • the verifier checks the signature on one element while the app reads an injected one.
  • TLS cross-protocol ServerKeyExchange (2012, TLS 1.2): see Negotiation and message state > Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)
    • signed ECDH parameters could be parsed by a client as DH parameters.
  • BREACH (2013, HTTP gzip responses): see Oracles and side channels > Compression oracles (CRIME and BREACH) (protocol, confidentiality)
    • compressed response bodies leaked CSRF tokens by length.
  • Lavabit key demand (2013, TLS server key): see Authentication and key exchange > Missing forward secrecy (KEM/DH, forward secrecy)
    • a compelled server private key would decrypt all recorded non-FS sessions.
  • Lucky13 (2013, TLS and DTLS CBC): see Oracles and side channels > Timing side channels (MAC, confidentiality, integrity)
    • the MAC runs over a padding-dependent length, so MAC timing leaks padding.
  • TIME (2013, HTTP responses): see Oracles and side channels > Compression oracles (CRIME and BREACH) (protocol, confidentiality)
    • browser-side timing measured compressed size, no network tap needed.
  • TLS truncation of logout (2013, HTTPS web apps): see Negotiation and message state > Truncation, reordering and dropped messages (AEAD, integrity)
    • dropping the end of a logout exchange left the session alive while the user believed it closed.
  • Cookie Cutter (2014, HTTPS): see Negotiation and message state > Truncation, reordering and dropped messages (AEAD, integrity)
    • truncating a response mid-header dropped the Secure flag from Set-Cookie.
  • Heartbleed (2014, TLS in OpenSSL): see Authentication and key exchange > Missing forward secrecy (KEM/DH, forward secrecy)
    • a heartbeat over-read leaked server private keys, which decrypt recorded non-FS traffic.
  • POODLE (2014, SSL 3.0 CBC): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • padding bytes are arbitrary and not MACed, so one byte leaks per about 256 requests.
  • POODLE over TLS (2014, TLS stacks): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • implementations that skipped the TLS padding check.
  • Triple Handshake (3SHAKE) (2014, TLS 1.2 resumption and renegotiation): see Authentication and key exchange > Unknown key share and missing identity binding (KEM/DH, auth)
    • the attacker syncs master secrets of two connections, so client auth on one carries to the other; fixed by RFC 7627.
  • FREAK (2015, TLS export RSA): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • client state machines accepted an export RSA ServerKeyExchange in a non-export suite.
  • KCI against TLS (2015, TLS 1.2 fixed (EC)DH client certificates): see Authentication and key exchange > Key compromise impersonation (KCI) (KEM/DH, auth)
    • with the client's certificate key, an attacker impersonates any server to that client.
  • Logjam (2015, TLS DHE_EXPORT): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • the attacker rewrites the suite to DHE_EXPORT; the 512-bit parameters are signed, the suite is not.
  • RollJam (2015, rolling-code car key fobs): see Negotiation and message state > Replay (protocol, freshness)
    • jam and record two codes, replay the first, keep the unused second for later.
  • SKIP-TLS and SMACK (2015, TLS state machines): see Authentication and key exchange > Unauthenticated key exchange and MITM (KEM/DH, auth)
    • clients accepted handshakes that skipped ServerKeyExchange or CertificateVerify, allowing impersonation.
  • TLS 1.3 and QUIC signature forgery (2015, TLS 1.3 drafts and QUIC): see Primitive misuse > Key reuse across purposes (KDF, integrity)
    • a PKCS#1 v1.5 decryption oracle on the same RSA key forged signatures.
  • TLS-ECDH invalid curve (2015, Java and other TLS-ECDH stacks): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • static ECDH keys were recovered from unvalidated points.
  • DROWN (2016, SSLv2 and TLS sharing an RSA key): see Primitive misuse > Key reuse across purposes (KDF, integrity)
    • an SSLv2 Bleichenbacher oracle decrypted TLS sessions.
  • Ethereum fork replay (2016, Ethereum and Ethereum Classic): see Negotiation and message state > Replay (protocol, freshness)
    • signed transactions had no chain id, so after the fork they were valid on both chains; EIP-155 adds it.
  • HEIST (2016, HTTPS via browser APIs): see Oracles and side channels > Compression oracles (CRIME and BREACH) (protocol, confidentiality)
    • browser timing APIs measured response sizes from JavaScript.
  • iMessage (2016, Apple iMessage): see Primitive misuse > ECB and unauthenticated encryption (block cipher, confidentiality, integrity)
    • unauthenticated AES-CTR let an attacker modify and re-sign ciphertexts to decrypt attachments.
  • Nonce-disrespecting adversaries (2016, TLS AES-GCM): see Primitive misuse > Nonce and IV reuse (AEAD, confidentiality, integrity)
    • servers repeated or randomly collided GCM nonces, allowing forgery.
  • Session ticket key reuse (2016, TLS 1.2 resumption): see Authentication and key exchange > Missing forward secrecy (KEM/DH, forward secrecy)
    • long-lived ticket keys let one key theft decrypt many past sessions.
  • SLOTH (2016, TLS 1.2, IKEv2, SSH): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • MD5 and SHA-1 transcript hashes allow transcript collisions for impersonation and downgrade.
  • SWEET32 (2016, TLS and OpenVPN with 3DES or Blowfish): see Primitive misuse > Nonce and IV reuse (AEAD, confidentiality, integrity)
    • 64-bit blocks collide after about 2^32 blocks in CBC, revealing plaintext XORs.
  • KRACK (2017, WPA2 four-way handshake): see Primitive misuse > Nonce and IV reuse (AEAD, confidentiality, integrity)
    • replaying handshake message 3 reinstalls the key and resets the nonce.
  • Measuring small subgroup attacks (2017, TLS, IPsec, SSH DH): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • many servers used non-safe groups without subgroup checks.
  • Monero key image (2017, CryptoNote Ed25519): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • cofactor-8 key images allowed double spends.
  • ROBOT (2017, TLS RSA key exchange): see Oracles and side channels > RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)
    • the 1998 oracle was still present in major TLS stacks and appliances.
  • Bluetooth fixed coordinate (2018, Bluetooth pairing): see Primitive misuse > Invalid curve and small subgroup (KEM/DH, confidentiality)
    • only the x coordinate was authenticated and y was not validated.
  • EFAIL (2018, S/MIME and OpenPGP): see Primitive misuse > ECB and unauthenticated encryption (block cipher, confidentiality, integrity)
    • CBC and CFB malleability injected exfiltration links into encrypted mail.
  • IKE key reuse (2018, IPsec IKEv1 and IKEv2): see Primitive misuse > Key reuse across purposes (KDF, integrity)
    • one RSA key across modes let a Bleichenbacher oracle in one mode break the others.
  • TLS 1.3 0-RTT replay (2018, TLS 1.3 early data): see Negotiation and message state > Replay (protocol, freshness)
    • early data can be replayed to the same or another server instance.
  • Dragonblood (2019, WPA3-SAE): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • downgrade to WPA2 in transition mode, plus timing and cache leaks of the password.
  • KNOB (2019, Bluetooth BR/EDR): see Negotiation and message state > Protocol downgrade (protocol, integrity)
    • unauthenticated key-length negotiation lowered session key entropy to 1 byte.
  • Nine lives of Bleichenbacher's CAT (2019, TLS RSA key exchange): see Oracles and side channels > RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)
    • cache side channels revived the oracle in patched libraries.
  • Selfie (2019, TLS 1.3 external PSK): see Authentication and key exchange > Reflection (MAC, auth)
    • with one PSK shared by a group, the attacker reflects a client's ClientHello back to it, so it talks to itself.
  • Zombie POODLE and GOLDENDOODLE (2019, TLS CBC in appliances): see Oracles and side channels > Padding oracle (block cipher, confidentiality)
    • observable padding checks in middleboxes.
  • Raccoon (2020, TLS 1.2 and earlier DH(E)): see Oracles and side channels > Timing side channels (MAC, confidentiality, integrity)
    • leading zero bytes of the DH secret are stripped before the KDF, so timing leaks a zero top byte.
  • SHA-1 is a Shambles (related, collision) (2020, PGP web of trust): see Primitive misuse > Hash length extension (hash/MAC, integrity)
    • a SHA-1 chosen-prefix collision forged key certifications.
  • ALPACA (2021, TLS across HTTPS, FTP, SMTP, IMAP, POP3): see Negotiation and message state > Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)
    • one certificate valid for several services lets an attacker redirect HTTPS to another protocol's server.

    • coerced domain controller authentication relayed to HTTP enrollment endpoints without channel binding.
  • Terrapin (2023, SSH): see Negotiation and message state > Truncation, reordering and dropped messages (AEAD, integrity)
    • the attacker shifts sequence numbers during the handshake and drops EXT_INFO, downgrading extensions undetected.

Authentication and key exchange

These attacks work because a handshake does not bind keys to the right peer, role or channel. Defense: authenticate the full transcript, identities and roles, with fresh ephemeral keys.

Unauthenticated key exchange and MITM (KEM/DH, auth)

  • Root cause
    • Key exchange alone gives a shared key with someone, not with the intended peer; anonymous DH is secure only against passive eavesdroppers.
      • An active attacker runs one DH with each side and relays, reading and editing everything.
    • Peer authentication is skipped or weakened: certificate checks disabled, hostnames unchecked, trust on first use (TOFU) without a pinned fingerprint, an unsigned handshake.
    • Source: RFC 8446 section 4.4 (TLS 1.3 authenticates with CertificateVerify and Finished); RFC 9525 (service identity checks).
  • Real cases
    • Disabled certificate validation in app code is a recurring finding (CWE-295, uncertain as a named source).
    • SSH TOFU: users accept an unknown host key at first connect (OpenSSH behavior, uncertain citation).
  • Known attacks:
    • SKIP-TLS and SMACK (2015, TLS state machines): clients accepted handshakes that skipped ServerKeyExchange or CertificateVerify, allowing impersonation (Beurdouche et al., IEEE S&P 2015).
  • Spot in C code
    • OpenSSL: SSL_CTX_set_verify(ctx, SSL_VERIFY_NONE, NULL), or a verify callback that always returns 1 (SSL_CTX_set_verify(3)).
    • OpenSSL: chain verified but no hostname check; the call SSL_set1_host(ssl, name) (or X509_check_host) is absent (SSL_set1_host(3)).
    • OpenSSL: SSL_get_verify_result ignored after the handshake, since without SSL_VERIFY_PEER a failed chain does not abort.
    • libcurl: CURLOPT_SSL_VERIFYPEER set to 0 or CURLOPT_SSL_VERIFYHOST set to 0 (libcurl docs).
    • A hand-rolled handshake that exchanges X25519 public keys (EVP_PKEY_get_raw_public_key) with no signature, MAC or pinned identity key over them.
  • Design defense
    • Authenticate the key exchange: sign the transcript with a long-term key the peer already trusts, or use a PSK or a Noise pattern with static keys (Noise spec, noiseprotocol.org).
    • Validate chain, hostname, expiry and revocation policy; pin a key or CA only when you control both ends and plan rotation.
    • Use mutual TLS or an application-layer signature when the server must identify clients (RFC 8446 section 4.3.2 CertificateRequest).
    • Keep verification-off switches out of release builds.

Reflection (MAC, auth)

  • Root cause
    • The attacker returns a party's own message (challenge, tag or ciphertext) to it, and the receiver accepts it as coming from the peer.
    • It works when both directions use the same key and message format, with no role, direction or identity in the authenticated data.
    • Textbook case: mutual challenge-response with a shared key. The attacker opens a second session and has the victim answer its own challenge.
      • Source: Boyd and Mathuria, "Protocols for Authentication and Key Establishment" (section uncertain).
  • Real case
    • SMB reflection (CVE-2008-4037 and the later NTLM relay family); the exact mapping is uncertain, verify before quoting.
  • Known attacks:
    • SMB NTLM reflection (2008, Windows SMB): the attacker returned a victim's NTLM challenge-response to the victim's own SMB server (MS08-068, CVE-2008-4037).
    • Selfie (2019, TLS 1.3 external PSK): with one PSK shared by a group, the attacker reflects a client's ClientHello back to it, so it talks to itself (Drucker and Gueron, IACR ePrint 2019/347).
  • Spot in C code
    • One key buffer used with HMAC() or an AEAD for both client-to-server and server-to-client messages.
    • Tag input is only the payload: no role byte, no sender id, no direction label.
    • Both sides use a counter nonce starting at zero under the same key: reflected or concurrent messages collide on a nonce (see nonce reuse).
    • A responder that signs or MACs whatever challenge it receives, even one it generated itself.
  • Design defense
    • Derive separate keys per direction with HKDF info labels; TLS 1.3 has distinct client and server traffic secrets and Finished keys (RFC 8446 section 7.1).
    • OpenSSL 3: derive both keys from one secret via EVP_KDF_fetch(NULL, "HKDF", NULL) with distinct info, such as c2s and s2c (EVP_KDF-HKDF(7)).
    • Put the sender role, both identities and a session id inside every MAC, signature or AEAD associated data.
    • A responder rejects a challenge equal to one it issued; bind each response to the challenge's origin.
  • Sources
    • RFC 8446 section 7.1; ISO/IEC 9798 discussion of reflection (uncertain, not re-fetched).

Unknown key share and missing identity binding (KEM/DH, auth)

  • Root cause
    • The handshake authenticates keys or key shares but not who each side believes the peer is.
      • Result: A and B share a key, but at least one of them believes it shares that key with someone else, such as the attacker.
    • Typical flaw: a signature covers the DH values but not the peer's identity, so an attacker registers the victim's public key under its own name.
      • Source: Blake-Wilson and Menezes, "Unknown key-share attacks on the station-to-station protocol", PKC 1999.
    • Related: the TLS triple handshake attack used session resumption to make two connections share a master secret (Bhargavan et al., IEEE S&P 2014).
  • Known attacks:
    • Lowe's attack on Needham-Schroeder (1995, Needham-Schroeder public key): message 2 omits B's identity, so an insider relays A's run and B believes it talks to A (Lowe, TACAS 1996).
    • STS unknown key share (1999, station-to-station): the attacker certifies the victim's public key under its own name (Blake-Wilson and Menezes, PKC 1999).
    • MQV unknown key share (2001, MQV key agreement): an online UKS attack on the protocol as specified (Kaliski, ACM TISSEC 2001 (uncertain)).
    • Triple Handshake (3SHAKE) (2014, TLS 1.2 resumption and renegotiation): the attacker syncs master secrets of two connections, so client auth on one carries to the other; fixed by RFC 7627.
      • Source: Bhargavan et al., IEEE S&P 2014.
  • Spot in C code
    • A signature over only the ephemeral public key or only a nonce: EVP_DigestSign(mctx, sig, &siglen, eph_pub, 32) with nothing else in the input.
    • KDF call with a constant info or context and no party identifiers or transcript hash.
    • Identity registration that lets any caller bind an existing public key to a new name (no proof of possession of the private key).
    • A resumption or session-ticket path that does not re-bind to the original peer identity.
  • Design defense
    • Sign or MAC the whole transcript including both identities and key shares; TLS 1.3 signs a hash of the handshake including the certificates (RFC 8446 section 4.4.3).
    • Put party identifiers in the KDF context (NIST SP 800-56A Rev 3, key derivation OtherInfo/FixedInfo; section number uncertain).
    • Add key confirmation (a MAC over the transcript under the new key), as TLS Finished does (RFC 8446 section 4.4.4).
    • Require proof of possession of the private key at registration.
    • TLS 1.2 fix for the triple handshake: the extended master secret (RFC 7627).

Missing channel binding (protocol, auth)

  • Root cause
    • A secret or credential is authenticated at the application layer (password, bearer token, SAML or OAuth response) but not tied to the secure channel it travels over (RFC 5056 section 1).
    • An attacker who terminates one TLS session with the victim and another with the server relays the credential and is accepted (Asokan, Niemi, Nyberg, 2003; venue uncertain).
      • Bearer tokens stolen from logs or proxies are replayed on a new connection (RFC 6750 section 5).
  • Known attacks:
    • SMBRelay (2001, NTLM over SMB): an NTLM exchange is relayed to another server; Extended Protection later added channel binding (Sir Dystic, 2001 (uncertain)).
    • Tunneled authentication MITM (2003, PEAP and other EAP tunnels): inner credentials not bound to the outer TLS tunnel are relayed into another tunnel.
      • Source: Asokan, Niemi, Nyberg, 2003 (venue uncertain).
    • TLS renegotiation attack (2009, TLS up to 1.2): the attacker sends a prefix, then the victim's handshake renegotiates the same connection and the server joins both; fixed by RFC 5746.
      • Source: CVE-2009-3555.
    • Triple Handshake (2014): also broke tls-unique; see Unknown key share and missing identity binding.
    • PetitPotam (2021, NTLM relay to AD CS): coerced domain controller authentication relayed to HTTP enrollment endpoints without channel binding (CVE-2021-36942 (mapping uncertain)).
  • Spot in C code
    • Login or token verification code that never reads anything from the TLS session (no SSL_export_keying_material call).
    • Token issued as a plain random string or unbound JWT with no cnf (confirmation) claim.
    • A custom protocol running inside TLS that authenticates with a password and no exporter value in the proof.
    • TLS-terminating proxies that forward identity in a header the backend trusts blindly.
  • Design defense
    • Mix a TLS exporter value into the authentication proof: RFC 5705 / RFC 8446 section 7.5; OpenSSL SSL_export_keying_material(3).
      • The old tls-unique binding (RFC 5929) is unsafe without the extended master secret; prefer tls-exporter (RFC 9266).
    • Sender-constrain tokens: mutual-TLS certificate-bound tokens (RFC 8705) or DPoP proofs (RFC 9449).
    • Short token lifetimes and audience restriction narrow the damage of a stolen bearer token (RFC 8725, section number uncertain).
  • Sources
    • RFC 5929, RFC 9266, RFC 8705, RFC 9449, RFC 7627; OpenSSL SSL_export_keying_material(3).

Key compromise impersonation (KCI) (KEM/DH, auth)

  • Root cause
    • After an attacker steals party A's long-term key, it can impersonate other parties to A, not only A to others.
    • It arises when A authenticates peers with a key A itself can compute: static-static DH, a shared MAC key, a PSK.
    • Source: Blake-Wilson, Johnson, Menezes, "Key agreement protocols and their security analysis", 1997.
  • Known attacks:
    • KCI against TLS (2015, TLS 1.2 fixed (EC)DH client certificates): with the client's certificate key, an attacker impersonates any server to that client (Hlauschek et al., WOOT 2015).
  • Spot in C code
    • Mutual authentication built only from static-static DH: EVP_PKEY_derive with both EVP_PKEYs long-term.
    • A symmetric PSK that both sides hold as the only authenticator (inherently KCI-prone: whoever has the PSK is any peer).
    • Client authentication by a shared HMAC key where the server also holds that key.
  • Design defense
    • Authenticate with a signature by the peer's private key over the transcript; TLS 1.3 certificate authentication does this (RFC 8446 section 4.4.3).
    • In Noise, pick patterns whose payload-security table resists KCI and mixes an ephemeral key (Noise spec section 7.7; section number uncertain).
    • Store the long-term key in an HSM or enclave and use per-session ephemeral keys so a stolen key cannot be used by itself.
    • Revoke and rotate on compromise.

Missing forward secrecy (KEM/DH, forward secrecy)

  • Root cause
    • Session keys depend on a long-term secret, so one later theft decrypts all recorded traffic.
    • RSA key transport encrypts the premaster secret to the server key; static-static DH has the same property.
    • Long-lived session ticket keys, resumption secrets and PSKs are also long-term secrets (Springall et al., "Measuring the Security Harm of TLS Crypto Shortcuts", IMC 2016; title from memory).
  • Known attacks:
    • Lavabit key demand (2013, TLS server key): a compelled server private key would decrypt all recorded non-FS sessions (court filings, 2013 (uncertain)).
    • Heartbleed (2014, TLS in OpenSSL): the heartbeat handler trusted the payload length and memcpy'd past the buffer, leaking memory including private keys (CVE-2014-0160; RFC 6520).
      • Without forward secrecy, a leaked RSA key decrypts recorded past traffic.
    • Session ticket key reuse (2016, TLS 1.2 resumption): long-lived ticket keys let one key theft decrypt many past sessions (Springall et al., IMC 2016).
  • Spot in C code
    • A key exchange using one X25519 or EC key generated at startup and used for every session (EVP_PKEY_keygen once).
    • Encrypting a session key to the peer's RSA public key (EVP_PKEY_encrypt, RSA_public_encrypt); RSA key-exchange suites in the cipher list.
    • Ephemeral key kept in a global or struct for reuse across sessions.
    • A ticket-encryption key that never rotates (OpenSSL ticket key callback or SSL_CTX_set_tlsext_ticket_keys).
    • Session keys logged, or not wiped after use (memset without OPENSSL_cleanse(3) or explicit_bzero(3)).
  • Design defense
    • Fresh ephemeral (EC)DH per session, deleted after use; all TLS 1.3 key exchange is ephemeral (RFC 8446 section 1.2).
    • Rotate ticket keys often and limit resumption lifetime.
    • Messaging uses a ratchet for forward secrecy and post-compromise security (Signal Double Ratchet specification).
    • Wipe secrets with OPENSSL_cleanse(3) or explicit_bzero(3); plain memset can be removed by the optimizer.

Negotiation and message state

These attacks replay, reorder, drop or move a message or option outside the state it was made for. Defense: authenticate negotiation, sequence, freshness and context with each message.

Protocol downgrade (protocol, integrity)

  • Root cause
    • Peers negotiate version or ciphers in the clear, and still support weak options for compatibility, so an on-path attacker steers both to the weakest common choice.
      • Source: Beurdouche et al., IEEE S&P 2015; Adrian et al., CCS 2015.
    • Fallback retries (resend a ClientHello with a lower version after a failure) let the attacker cause the failure (RFC 7507 section 1).
    • The negotiation messages are not covered by a MAC or signature that is verified under strong keys (RFC 8446 section 4.4.4 shows the fix: Finished covers them).
  • TLS 1.3 defenses and why they are not enough alone
    • A 1.3 server that negotiates 1.2 writes DOWNGRD plus 0x01 into the last 8 bytes of ServerHello.random (0x00 for 1.1 or below). A 1.3 client seeing it aborts (RFC 8446 section 4.1.3).
      • TLS 1.2 (EC)DHE signs both randoms in ServerKeyExchange, so the sentinel cannot be stripped. Static RSA suites have no such signature.
    • The 1.3 transcript (CertificateVerify, Finished) covers ClientHello and ServerHello, so a 1.3 cipher cannot be changed in flight.
      • It does not cover a retry with a different ClientHello, nor a break of the weak crypto in real time.
    • TLS_FALLBACK_SCSV signals a deliberate fallback so a server can refuse it (RFC 7507).
  • Real cases
    • FREAK (2015): clients accepted 512-bit export RSA keys they never asked for; servers reused one key, which the attacker factored in hours (Beurdouche et al., IEEE S&P 2015).
    • Logjam (2015): the attacker pushed DHE to 512-bit export groups, and precomputation made each discrete log take about a minute (Adrian et al., CCS 2015).
      • The TLS 1.2 ServerKeyExchange signature covers the randoms and DH parameters but not the chosen suite, so export parameters pass as normal DHE.
    • POODLE (2014): fallback to SSL 3.0 enabled the CBC padding oracle (RFC 7568 deprecates SSL 3.0).
    • DROWN (2016): SSLv2 on the same key broke TLS sessions (see key reuse).
    • STARTTLS stripping: the attacker removes the upgrade offer from a plaintext SMTP or IMAP session (RFC 8314 discusses; HSTS, RFC 6797, fixes this for HTTP).
  • Known attacks:
    • SSL 2.0 cipher suite rollback (1996, SSL 2.0): handshake messages were unauthenticated, so the attacker removed strong suites (Wagner and Schneier, USENIX Electronic Commerce 1996).
    • SSLstrip (2009, HTTP to HTTPS upgrade): an on-path attacker rewrites https links to http and proxies; HSTS (RFC 6797) fixes it (Marlinspike, Black Hat DC 2009).
    • POODLE (2014): downgrade dance to SSL 3.0; see Padding oracle.
    • FREAK (2015, TLS export RSA): client state machines accepted an export RSA ServerKeyExchange in a non-export suite (CVE-2015-0204; Beurdouche et al., IEEE S&P 2015).
    • Logjam (2015, TLS DHE_EXPORT): the attacker rewrites the suite to DHE_EXPORT; the 512-bit parameters are signed, the suite is not (Adrian et al., CCS 2015).
    • DROWN (2016): SSLv2 on the same RSA key; see Key reuse across purposes.
    • SLOTH (2016, TLS 1.2, IKEv2, SSH): MD5 and SHA-1 transcript hashes allow transcript collisions for impersonation and downgrade (Bhargavan and Leurent, NDSS 2016).
    • Dragonblood (2019, WPA3-SAE): downgrade to WPA2 in transition mode, plus timing and cache leaks of the password (Vanhoef and Ronen, IEEE S&P 2020).
    • KNOB (2019, Bluetooth BR/EDR): unauthenticated key-length negotiation lowered session key entropy to 1 byte (Antonioli et al., USENIX Security 2019; CVE-2019-9506).
    • Terrapin (2023): strips SSH extension negotiation; see Truncation, reordering and dropped messages.
  • Spot in C code
    • OpenSSL: no SSL_CTX_set_min_proto_version(ctx, TLS1_2_VERSION), or SSLv23_method/SSL_OP_ALL defaults with legacy versions and suites left on (SSL_CTX_set_min_proto_version(3)).
    • Cipher lists containing EXPORT, RC4, 3DES, NULL or aNULL, and DH parameters of 1024 bits or less.
    • A client that retries SSL_connect with a lower version after failure.
    • Own protocol: a version byte read before authentication and used to select looser parsing, with no minimum.
    • Negotiated parameters not included in the data passed to the signature or key derivation.
  • Design defense
    • Remove weak options instead of negotiating them; set a minimum version.
    • Authenticate the full negotiation transcript under keys the attacker cannot break; never fall back silently.
    • Plaintext-to-TLS upgrades must fail closed (implicit TLS, RFC 8314) or be pinned (HSTS).
    • Current TLS guidance: RFC 9325 (BCP 195).

Replay (protocol, freshness)

  • Root cause
    • A valid message is accepted twice. A MAC or signature over the body proves who sent it, not when, nor that it is the first time (RFC 8446 section 8 for the TLS case).
    • Servers keep no state, the state is per instance (so a replay hits another node), or the check is racy (check then insert); deployment patterns are our reasoning (uncertain).
  • Known attacks:
    • RollJam (2015, rolling-code car key fobs): jam and record two codes, replay the first, keep the unused second for later (Kamkar, DEF CON 23 (uncertain)).
    • Ethereum fork replay (2016, Ethereum and Ethereum Classic): signed transactions had no chain id, so after the fork they were valid on both chains; EIP-155 adds it (EIP-155).
    • KRACK (2017): replays handshake message 3 to reset nonces; see Nonce and IV reuse.
    • TLS 1.3 0-RTT replay (2018, TLS 1.3 early data): early data can be replayed to the same or another server instance (RFC 8446 section 8).
  • Spot in C code
    • Request tag is HMAC(EVP_sha256(), key, .., body, ..) with no timestamp, nonce or sequence number in the MACed data.
    • Timestamp present but compared with a huge window, or the nonce cache is never pruned (memory growth) or pruned on a shorter interval than the window.
    • A lookup followed by a separate insert in a nonce table shared by threads without a lock, or a per-process table behind a load balancer.
    • Method, path, host or audience missing from the MACed data, so a signed request replays on another endpoint.
    • Session or JWT tokens with no exp, jti or audience (RFC 7519 section 4.1).
  • Design defense
    • MAC a timestamp plus a unique nonce or per-client counter, with method, path, host and query; reject stale and seen values.
      • Use an atomic insert in a shared store keyed by the nonce, with a TTL equal to the window.
    • Idempotency keys for state-changing calls limit duplicate effects.
    • Datagram protocols use a sliding anti-replay window over sequence numbers (RFC 6347 section 4.1.2.6; RFC 9147 for DTLS 1.3).
    • TLS 1.3 0-RTT data is replayable across connections (RFC 8446 section 8); servers need single-use tickets or ClientHello recording (sections 8.1 and 8.2).
      • Send only safe methods in early data; the server may answer 425 Too Early (RFC 8470).
      • OpenSSL: early data is opt-in on the server (SSL_CTX_set_max_early_data; SSL_CTX_set_max_early_data(3)); leave it off unless handlers are replay-safe.
    • AWS SigV4 signs a timestamp and rejects requests older than 5 minutes (AWS docs).
  • Sources
    • RFC 6347 section 4.1.2.6; RFC 9147; RFC 8446 sections 8, 8.1, 8.2; RFC 8470; RFC 7519; AWS SigV4 docs; OpenSSL SSL_CTX_set_max_early_data(3).

Truncation, reordering and dropped messages (AEAD, integrity)

  • Root cause
    • Each chunk or message is authenticated alone, but nothing authenticates the sequence or the end.
      • The attacker drops the tail, swaps chunks or splices two streams, and every remaining piece verifies.
    • TLS close handling: an attacker injecting TCP FIN or RST truncates data unless the application requires a close_notify alert (RFC 8446 section 6.1).
  • Known attacks:
    • TLS truncation of logout (2013, HTTPS web apps): dropping the end of a logout exchange left the session alive while the user believed it closed (Smyth and Pironti, WOOT 2013).
    • Cookie Cutter (2014, HTTPS): truncating a response mid-header dropped the Secure flag from Set-Cookie (Bhargavan et al., IEEE S&P 2014).
    • Terrapin (2023, SSH): the attacker shifts sequence numbers during the handshake and drops EXT_INFO, downgrading extensions undetected.
      • Source: Bäumer, Brinkmann, Schwenk, "Terrapin Attack: Breaking SSH Channel Integrity By Sequence Number Manipulation", USENIX Security 2024; CVE-2023-48795.
  • Spot in C code
    • Chunked file or stream encryption with an independent random nonce per chunk and one EVP_aes_256_gcm() call per chunk with no chunk index or last flag.
    • Decrypt loops that end on EOF or a length field and treat that as success.
    • SSL_read returning 0 or an error treated as end of data without checking SSL_get_shutdown or SSL_ERROR_ZERO_RETURN (SSL_read(3)).
    • Length-prefixed frames whose length is outside the authenticated data.
  • Design defense
    • Use the STREAM construction: the nonce holds a chunk counter and a last-chunk flag, so truncation and reordering fail authentication (Hoang et al., CRYPTO 2015).
      • OpenSSL has no STREAM API: build the GCM nonce from a 64-bit chunk counter and a last-chunk byte; the reader requires the final chunk (our construction, uncertain).
      • age encrypts 64 KiB chunks this way (age specification).
    • Authenticate the total length or an end marker; require close_notify at the application layer.
    • Per-direction sequence numbers inside the MAC or nonce, as TLS does (RFC 8446 section 5.3).

Missing context binding (cut-and-paste and cross-protocol use) (protocol, integrity)

  • Root cause
    • A valid ciphertext, tag or signature is accepted in a place it was not made for: another row, user, field, message type, protocol version or protocol.
      • Source: RFC 5116 section 2.1; Somorovsky et al., USENIX Security 2012.
    • Ambiguous encoding of concatenated fields (a || b equal for different splits) lets an attacker move bytes between fields (NIST SP 800-185 TupleHash exists to prevent this).
    • Hashes and signatures reused for several purposes with no label allow cross-protocol substitution (Mavrogiannopoulos et al., CCS 2012; Brinkmann et al., USENIX Security 2021).
  • Known attacks:
    • STARTTLS command injection (2011, SMTP, IMAP, POP3): plaintext commands sent before STARTTLS were processed as if received over TLS (CVE-2011-0411).
    • SAML signature wrapping (2012, SAML single sign-on): the verifier checks the signature on one element while the app reads an injected one (Somorovsky et al., USENIX Security 2012).
    • TLS cross-protocol ServerKeyExchange (2012, TLS 1.2): signed ECDH parameters could be parsed by a client as DH parameters (Mavrogiannopoulos et al., CCS 2012).
    • ALPACA (2021, TLS across HTTPS, FTP, SMTP, IMAP, POP3): one certificate valid for several services lets an attacker redirect HTTPS to another protocol's server.
      • Source: Brinkmann et al., USENIX Security 2021.
  • Spot in C code
    • AEAD call with empty associated data on data that belongs to a user, row or message type.
    • OpenSSL GCM encryption with no EVP_EncryptUpdate(ctx, NULL, &len, aad, aad_len) call before the plaintext.
    • Hash or MAC input built with memcpy or snprintf of variable-length fields with no length prefix or separator.
    • Signing raw bytes with the same key for tokens, API requests and uploads.
    • HKDF (EVP_KDF HKDF, OSSL_KDF_PARAM_INFO) with an empty or constant info for different outputs (EVP_KDF-HKDF(7)).
  • Design defense
    • Put identifiers in the AEAD associated data (table, column, row id, key version); the receiver rebuilds it, it is not stored with the ciphertext (RFC 5116 sections 2.1 and 2.2).
    • Length-prefix or use a canonical, unambiguous encoding for every authenticated tuple.
    • Add a purpose label and version to every hash, MAC, signature and KDF call.
      • TLS 1.3 CertificateVerify signs 64 spaces, a context string and a zero byte before the transcript hash (RFC 8446 section 4.4.3).
    • The database-swap scenario is our reasoning from RFC 5116, not a cited incident (uncertain).

Oracles and side channels

These attacks learn secrets one query at a time from errors, timing or length. Defense: one uniform error after authentication, constant-time code, no secrets mixed with attacker data.

Padding oracle (block cipher, confidentiality)

  • Root cause
    • A CBC decryptor reveals whether the padding is valid, by an error code, message or timing, before it authenticates the ciphertext.
    • CBC decryption is P_i = D_K(C_i) xor C_(i-1) (SP 800-38A section 6.2), so a byte flipped in C_(i-1) flips the same byte of P_i.
    • PKCS#7 padding appends n bytes of value n (1 to 16 for AES); the decryptor checks all n (RFC 5652 section 6.3; section uncertain).
    • The attacker changes bytes in the previous ciphertext block and watches the verdict.
      • A valid verdict means the last plaintext byte probably became 0x01, which reveals one byte of D_K(C_i); about 128 queries per byte.
    • The attack recovers plaintext (and, as CBC-R, can build chosen plaintext) but never the key (Vaudenay, EUROCRYPT 2002).
    • Variants: Lucky Thirteen read TLS CBC plaintext from MAC timing (AlFardan and Paterson, IEEE S&P 2013); POODLE used SSL 3.0 padding (2014); ASP.NET (Duong and Rizzo, IEEE S&P 2011).
  • Known attacks:
    • Vaudenay padding oracle (2002, CBC in SSL, IPsec, WTLS): a valid-padding verdict decrypts CBC byte by byte (Vaudenay, EUROCRYPT 2002).
    • Canvel et al. (2003, IMAP over TLS): timing told padding errors from MAC errors and recovered passwords (Canvel, Hiltgen, Vaudenay, Vuagnoux, CRYPTO 2003).
    • SSH CBC plaintext recovery (2009, SSH binary packet protocol): the encrypted length field was processed before the MAC check (Albrecht, Paterson, Watson, IEEE S&P 2009).
    • XML Encryption (2011, W3C XML Encryption CBC): parsing errors after decryption formed an oracle (Jager and Somorovsky, CCS 2011).
    • POODLE (2014, SSL 3.0 CBC): padding bytes are arbitrary and not MACed, so one byte leaks per about 256 requests (Moller, Duong, Kotowicz, 2014; CVE-2014-3566).
    • POODLE over TLS (2014, TLS stacks): implementations that skipped the TLS padding check (CVE-2014-8730).
    • Zombie POODLE and GOLDENDOODLE (2019, TLS CBC in appliances): observable padding checks in middleboxes (Young, 2019 (uncertain)).
  • Spot in C code
    • EVP_aes_*_cbc() decryption where EVP_DecryptFinal_ex failure (bad padding) is reported differently from a later MAC failure (EVP_DecryptInit(3)).
    • Encrypt-and-MAC or MAC-then-encrypt with CBC; a MAC check placed after the unpad step.
    • Distinct HTTP status, log line or response time for "bad padding" and "bad MAC".
    • Manual pad_len = buf[len-1] handling with early returns.
  • Design defense
    • Use an AEAD (AES-GCM, ChaCha20-Poly1305), which authenticates before releasing plaintext.
    • If CBC is unavoidable: encrypt-then-MAC, verify the MAC over IV and ciphertext in constant time first, and return one generic error (RFC 7366 for TLS).
    • Same error text, status and timing for every decryption failure.
  • Sources
    • Vaudenay 2002; RFC 7366; Bellare and Namprempre, ASIACRYPT 2000.

RSA PKCS#1 v1.5 decryption oracle (Bleichenbacher) (KEM/DH, confidentiality)

  • Root cause
    • An oracle tells the attacker whether a decrypted RSA ciphertext has valid PKCS#1 v1.5 padding.
      • RSA is malleable, so the attacker multiplies the ciphertext by s^e and narrows the plaintext interval from many queries (Bleichenbacher, CRYPTO 1998).
    • The oracle may be an error code, an alert, a timing difference or a connection reset.
    • ROBOT (2017) found it still present in major TLS stacks (USENIX Security 2018). Marvin (2023) is the timing variant (Kario; source not re-fetched, uncertain).
    • Signatures can also be forged under the same key if a decryption oracle exists (see key reuse).
  • Known attacks:
    • Bleichenbacher 1998 (1998, SSL 3.0 RSA key exchange): a padding error distinct from other errors was an oracle; about a million queries recover the premaster secret (Bleichenbacher, CRYPTO 1998).
    • Klima-Pokorny-Rosa (2003, TLS RSA key exchange): the premaster version-number check became a new oracle (Klima, Pokorny, Rosa, CHES 2003).
    • DROWN (2016): SSLv2 Bleichenbacher oracle used on TLS; see Key reuse across purposes.
    • ROBOT (2017, TLS RSA key exchange): the 1998 oracle was still present in major TLS stacks and appliances (Bock, Somorovsky, Young, USENIX Security 2018).
    • Nine lives of Bleichenbacher's CAT (2019, TLS RSA key exchange): cache side channels revived the oracle in patched libraries (Ronen et al., IEEE S&P 2019).
  • Spot in C code
    • RSA_private_decrypt(.., RSA_PKCS1_PADDING) or EVP_PKEY_CTX_set_rsa_padding(ctx, RSA_PKCS1_PADDING) on decrypt.
    • A TLS server or custom protocol that accepts RSA key transport.
    • Error paths that differ in message, status code or time for bad padding versus bad content (ERR_get_error codes returned to the peer).
  • Design defense
    • Do not use RSA encryption in new designs; use a KEM or HPKE (RFC 9180) and ECDHE.
    • If RSA is needed: RSA_PKCS1_OAEP_PADDING, with one undifferentiated error and no timing difference (RFC 8017 section 7.1; the OAEP decoding step must also be constant time).
    • TLS 1.3 removed RSA key transport (RFC 8446 section 1.2).
    • Implicit rejection: return a random fake plaintext instead of an error (RFC 5246 section 7.4.7.1 for TLS 1.2).
      • Recent OpenSSL versions add implicit rejection to PKCS#1 v1.5 decryption (version uncertain).

Timing side channels (MAC, confidentiality, integrity)

  • Root cause
    • Execution time, memory access pattern or branches depend on secret data, so an observer infers the secret from measured time.
    • Early-exit comparison: memcmp and strcmp may return at the first differing byte, so response time grows with the length of the matching prefix.
      • An attacker recovers a MAC tag byte by byte, about 256 * tag_len guesses times the samples needed, instead of 2^(8 * tag_len).
    • Remote timing is measurable with enough samples (Brumley and Boneh, USENIX Security 2003; Crosby et al. 2009).
    • Other sources: secret-indexed table lookups (table-based AES leaks through cache timing; Bernstein 2005), secret-dependent branches, variable-time big-integer code (Marvin).
  • Known attacks:
    • Lucky13 (2013, TLS and DTLS CBC): the MAC runs over a padding-dependent length, so MAC timing leaks padding (AlFardan and Paterson, IEEE S&P 2013).
    • Raccoon (2020, TLS 1.2 and earlier DH(E)): leading zero bytes of the DH secret are stripped before the KDF, so timing leaks a zero top byte (Merget et al., USENIX Security 2021).
  • Spot in C code
    • memcmp(computed, received, n) == 0, strcmp or strncmp on MACs, tokens, password hashes or API keys; also hex or base64 strings compared this way.
    • Hand-written loops with break or return on the first mismatch.
    • if (secret_bit) { .. }, table[secret_byte], % or / on secrets in hand-written code.
    • Hand-written crypto in place of audited libraries; ladder or table code with branches on key bits.
int check(const uint8_t key[32], const uint8_t *msg, size_t n,
          const uint8_t tag[32]) {
    uint8_t mac[32];
    unsigned int len = sizeof mac;
    HMAC(EVP_sha256(), key, 32, msg, n, mac, &len);
    /* Constant time: CRYPTO_memcmp, not memcmp. */
    return CRYPTO_memcmp(mac, tag, 32) == 0;
}
  • Design defense
    • OpenSSL CRYPTO_memcmp(3) (constant time, equality only) after checking lengths, which are public.
    • Use library implementations built for constant-time execution (AES-NI or bitsliced AES, ChaCha20, OpenSSL X25519).
    • Compilers can undo constant-time source; check the generated code or use tools such as dudect (uncertain).
    • Avoid secret-dependent timing in error paths: same work and same response for every failure.
  • Sources
    • OpenSSL CRYPTO_memcmp(3); Brumley and Boneh 2003; Bernstein, "Cache-timing attacks on AES", 2005.

Compression oracles (CRIME and BREACH) (protocol, confidentiality)

  • Root cause
    • Compression makes length depend on content, and encryption preserves length.
      • When attacker-chosen data is compressed together with a secret, a guess matching the secret compresses better and the ciphertext shrinks.
    • The attacker repeats the guess byte by byte and recovers cookies or tokens; it leaks secrets in the plaintext, not keys.
    • CRIME (2012) used TLS-level compression; TLS 1.3 removed it (legacy_compression_methods must be the single null method, RFC 8446 section 4.1.2).
    • BREACH (2013) uses HTTP body gzip, so TLS 1.3 does not help when a response holds a secret and reflected input (Gluck, Harris, Prado, Black Hat 2013).
  • Known attacks:
    • VoIP VBR phrase spotting (2008, SRTP with VBR codecs): packet lengths of encrypted calls revealed spoken phrases (Wright et al., IEEE S&P 2008).
    • CRIME (2012, TLS and SPDY compression): compressed request headers leaked cookies by length (Rizzo and Duong, Ekoparty 2012; CVE-2012-4929).
    • BREACH (2013, HTTP gzip responses): compressed response bodies leaked CSRF tokens by length (Gluck, Harris, Prado, Black Hat USA 2013).
    • TIME (2013, HTTP responses): browser-side timing measured compressed size, no network tap needed (Be'ery and Shulman, Black Hat Europe 2013).
    • HEIST (2016, HTTPS via browser APIs): browser timing APIs measured response sizes from JavaScript (Vanhoef and Van Goethem, Black Hat USA 2016).
  • Spot in C code
    • zlib deflate or compress2 (or zstd, brotli) followed by encryption of a message that mixes a secret with attacker-influenced data.
    • OpenSSL builds with TLS compression enabled (SSL_OP_NO_COMPRESSION not set on old versions).
    • HTTP responses with gzip or brotli enabled that echo input next to a CSRF token or session secret.
    • Messages whose compressed length reaches an observer, such as on a network trace.
  • Design defense
    • Do not compress messages that carry secrets, or compress secrets and attacker data in separate contexts.
    • Per-request masked CSRF tokens (random mask each response), SameSite cookies and rate limits against repeated guesses.
    • Pad lengths only as defense in depth (it raises cost, not a fix; uncertain).
  • Sources
    • Rizzo and Duong, "The CRIME Attack", Ekoparty 2012; RFC 7457 section 2.6; RFC 8446 section 4.1.2.

Primitive misuse

These attacks use a sound primitive outside its contract: repeated nonces, no MAC, raw hash as MAC, bad randomness, shared keys, unchecked points. Defense: misuse-resistant APIs and checks.

Nonce and IV reuse (AEAD, confidentiality, integrity)

  • Root cause
    • A stream-cipher-based AEAD (AES-GCM, ChaCha20-Poly1305) derives its keystream from key and nonce, so a repeated nonce repeats the keystream.
    • Confidentiality: C1 xor C2 = P1 xor P2; a known or guessable P1 reveals P2.
    • Integrity (GCM): two tags under one nonce let the attacker solve for the GHASH key H = E_K(0^128) and forge tags for chosen ciphertexts (Joux's forbidden attack).
      • H is not the master key K, so other nonces stay confidential, but forgery works for any nonce under which the attacker has seen one valid tag.
      • Tag: T = GHASH_H(A, C) xor E_K(J0), J0 from the nonce; a repeated nonce cancels E_K(J0) in T1 xor T2, leaving a polynomial in H (SP 800-38D sections 6.4, 7.1).
      • ChaCha20-Poly1305: a reused nonce reuses the Poly1305 one-time key, which also allows forgery.
    • Random 96-bit nonces collide by the birthday bound: NIST caps a key at 2^32 random-nonce messages (SP 800-38D section 8.3).
      • With q random 96-bit nonces, collision probability is about q^2 / 2^97; at q = 2^32 that is 2^-33, under the 2^-32 target (target from SP 800-38D section 8, uncertain).
    • Real cases: TLS servers repeating GCM nonces (Boeck et al., WOOT 2016); WPA2 KRACK reset the nonce by replaying a handshake message (Vanhoef and Piessens, CCS 2017).
  • Known attacks:
    • WEP (2001, 802.11 WEP): 24-bit IVs repeat keystreams, and RC4 with the IV prefixed to the key leaks the key (Fluhrer, Mantin, Shamir, SAC 2001).
    • BEAST (2011, TLS 1.0 CBC): the next record's IV was the last ciphertext block, so it was predictable, enabling byte-at-a-time cookie recovery (Duong and Rizzo, Ekoparty 2011; CVE-2011-3389).
    • Nonce-disrespecting adversaries (2016, TLS AES-GCM): servers repeated or randomly collided GCM nonces, allowing forgery (Bock et al., WOOT 2016).
    • SWEET32 (2016, TLS and OpenVPN with 3DES or Blowfish): 64-bit blocks collide after about 2^32 blocks in CBC, revealing plaintext XORs (Bhargavan and Leurent, CCS 2016; CVE-2016-2183).
    • KRACK (2017, WPA2 four-way handshake): replaying handshake message 3 reinstalls the key and resets the nonce (Vanhoef and Piessens, CCS 2017; CVE-2017-13077).
  • Spot in C code
    • uint8_t nonce[12] = {0}; or a string-literal nonce passed to EVP_EncryptInit_ex.
    • Nonce derived from a message field or a low-resolution timestamp (time(NULL)).
    • Counter nonce in a static variable only (restart, crash recovery or a restored VM snapshot resets it), or per-process counters when several processes or nodes share a key.
    • Both directions starting from counter zero with the same key (see reflection).
    • Random 96-bit nonces (RAND_bytes(nonce, 12)) on a key that encrypts more than about 2^32 messages.
    • Retry paths that re-encrypt a modified message under the same nonce.
int seal(EVP_CIPHER_CTX *ctx, const unsigned char key[32],
         const unsigned char *m, int mlen, unsigned char *c) {
    /* Finding: fixed nonce, every call reuses the keystream. */
    static const unsigned char iv[12] = {0};
    int len;
    EVP_EncryptInit_ex(ctx, EVP_aes_256_gcm(), NULL, key, iv);
    return EVP_EncryptUpdate(ctx, c, &len, m, mlen);
}
  • Design defense
    • Persisted or per-sender counter nonces with sender id in the nonce; TLS 1.3 XORs a per-direction static IV with the record sequence number (RFC 8446 section 5.3).
    • XChaCha20-Poly1305: 192-bit nonces make random nonces safe for practical volumes (draft-irtf-cfrg-xchacha); not an OpenSSL EVP cipher (uncertain).
    • AES-GCM-SIV (RFC 8452): the tag is the CTR IV, so reuse only leaks equality of (nonce, AD, plaintext). It needs two passes, so it cannot stream.
    • Rotate keys by message count; derive per-message keys with HKDF.
  • Sources
    • NIST SP 800-38D sections 7 and 8.3; Joux 2006 comment to NIST; RFC 8439; RFC 8452.

ECB and unauthenticated encryption (block cipher, confidentiality, integrity)

  • Root cause
    • ECB encrypts each 16-byte block independently, so equal plaintext blocks give equal ciphertext blocks and structure leaks (SP 800-38A section 6.1).
      • With an attacker-controlled prefix it also allows byte-at-a-time recovery of an appended secret (Cryptopals; uncertain as a source).
    • Unauthenticated CTR (and stream ciphers): C = P xor keystream, so flipping bit i of C flips bit i of P with no error.
      • With a known field, the attacker XORs in known xor wanted to rewrite role=user into role=root.
    • Unauthenticated CBC: flipping a bit in C_(i-1) flips the same bit in P_i and garbles P_(i-1). EFAIL (2018) used CBC and CFB malleability in S/MIME and OpenPGP mail.
    • MAC order: encrypt-then-MAC lets the receiver reject tampering before decrypting, so there is no decryption oracle.
      • MAC-then-encrypt with CBC must decrypt and unpad first (padding oracle). Encrypt-and-MAC with a deterministic MAC leaks equal plaintexts.
  • Known attacks:
    • WEP bit flipping (2001, 802.11 WEP): CRC-32 is linear and the cipher a stream, so bits flip and the checksum is fixed up (Borisov, Goldberg, Wagner, MobiCom 2001).
    • iMessage (2016, Apple iMessage): unauthenticated AES-CTR let an attacker modify and re-sign ciphertexts to decrypt attachments (Garman et al., USENIX Security 2016).
    • EFAIL (2018, S/MIME and OpenPGP): CBC and CFB malleability injected exfiltration links into encrypted mail (Poddebniak et al., USENIX Security 2018).
  • Spot in C code
    • EVP_aes_*_ecb(), AES_ecb_encrypt or AES_encrypt called per block in a loop.
    • EVP_aes_*_ctr(), _cbc() or _cfb() with no MAC step, or a MAC computed over plaintext only.
    • GCM decrypt where the EVP_CTRL_AEAD_SET_TAG / EVP_DecryptFinal_ex result is ignored, so unverified plaintext is used (EVP_EncryptInit(3)).
    • Tag over the ciphertext but not the IV, nonce or associated data.
    • Encrypted cookies or tokens decoded and trusted without authentication.
  • Design defense
    • Use an AEAD, which authenticates the ciphertext before releasing plaintext (RFC 5116): OpenSSL EVP_aes_256_gcm() or EVP_chacha20_poly1305() with AAD set via EVP_EncryptUpdate(ctx, NULL, ..).
    • If composing by hand: encrypt-then-MAC over IV, ciphertext and AD with an independent MAC key (Bellare and Namprempre 2000).
    • Release no plaintext until the tag check returns success.
  • Sources
    • NIST SP 800-38A sections 6.1 and 6.5; EFAIL, USENIX Security 2018.

Hash length extension (hash/MAC, integrity)

  • Root cause
    • A Merkle-Damgard hash (MD5, SHA-1, SHA-256, SHA-512) outputs its full internal state, so H(m) is a valid starting state for hashing more data.
    • With tag = H(secret || m), the attacker knows tag, m and the length of secret.
      • It sets the hash state to tag and keeps hashing ext, producing a valid tag for secret || m || pad || ext without the secret.
    • It is a forgery; the secret stays unknown. Real case: Flickr API signatures MD5(secret || params) (Duong and Rizzo, 2009).
    • Why the glue padding is needed
      • The hash only releases its state after the padded message was processed: secret || m || 0x80 || zeros || 64-bit bit length.
        • The padded input is a whole number of blocks (64 bytes for SHA-256; FIPS 180-4 section 5.1.1).
      • The forged message must start with exactly those bytes, so the old padding becomes part of the message. This is the glue padding, and the verifier recomputes the same total.
    • Why the attacker needs the secret length
      • The glue padding contains the bit length of secret || m, and the new padding at the end contains the total length including secret, so both depend on it.
      • The length is guessed by trying plausible values (often 8 to 64 bytes); a wrong guess yields an invalid tag.
  • Known attacks:
    • Rogue CA (related, collision) (2008, X.509 with MD5): an MD5 chosen-prefix collision turned a site certificate into a CA certificate (Stevens et al., CRYPTO 2009).
    • Flickr API signature forgery (2009, Flickr API): MD5(secret || params) signatures were extended with new parameters (Duong and Rizzo, 2009).
    • SHA-1 is a Shambles (related, collision) (2020, PGP web of trust): a SHA-1 chosen-prefix collision forged key certifications (Leurent and Peyrin, USENIX Security 2020).
  • Spot in C code
    • SHA256_Init, SHA256_Update(&c, secret, ..), SHA256_Update(&c, msg, ..), SHA256_Final used as authentication.
    • EVP_Digest over a buffer built as secret || msg, compared with a client-supplied value.
    • Home-made H(key || data), H(data || key) (still weak against collisions) or H(key || data || key) constructions.
    • Plain SHA-2 calls where a keyed primitive (HMAC or EVP_MAC_fetch(NULL, "HMAC", NULL)) is needed.
  • Design defense
    • HMAC (RFC 2104): the outer hash hides the inner state.
    • SHA-3 and KMAC are sponges: the output exposes only the rate part, and the hidden capacity (512 bits for SHA3-256) would have to be guessed to resume the state (FIPS 202).
      • If the capacity leaked, the attacker could continue absorbing as if it knew the state, so it is the part that carries security.
    • Keyed BLAKE2 (OpenSSL 3 BLAKE2BMAC, EVP_MAC-BLAKE2(7)) or BLAKE3; KMAC (EVP_MAC-KMAC(7)); truncated SHA-2 (SHA-384, SHA-512/256) hides part of the state.
  • Sources
    • FIPS 180-4; RFC 2104; FIPS 202; Duong and Rizzo, "Flickr's API Signature Forgery Vulnerability", 2009.

Weak or misused RNG (RNG, confidentiality)

  • Root cause
    • Keys, nonces or signature randomness come from a predictable, low-entropy or duplicated source, so an attacker enumerates or recomputes them.
    • Low boot entropy: headless devices generated RSA keys at first boot before the Linux pool was seeded, and many drew the same first prime.
      • Two moduli sharing a prime fall to gcd(N1, N2) = p, then q = N1 / p; this factored about 0.5% of TLS hosts' keys (Heninger et al., USENIX Security 2012).
      • Batch GCD scales it: a product tree gives P = N1 * .. * Nk, a remainder tree gives z_i = P mod N_i^2, and gcd(N_i, z_i / N_i) exposes shared primes (Heninger et al. 2012).
    • Debian OpenSSL (2006 to 2008) generated keys from a tiny seed space of process ids (CVE-2008-0166; detail from memory).
    • ECDSA: a repeated k gives k = (z1 - z2) / (s1 - s2) mod n then d = (s1 k - z1) / r mod n. A biased k falls to lattice attacks (hidden number problem).
      • Real cases: Sony PS3 constant k (fail0verflow, 2010); Android SecureRandom bug, 2013; Minerva and TPM-Fail, 2020.
  • Spot in C code
    • rand(), random(), drand48() or srand(time(NULL)) anywhere near keys, nonces, tokens or salts.
    • RAND_bytes return value ignored (it returns 1 on success; RAND_bytes(3)), or the deprecated RAND_pseudo_bytes.
    • Reading /dev/urandom without checking the read length, or key generation at first boot before the OS pool is seeded (getrandom(2) with no flags blocks until initialized).
    • A DRBG state copied by fork or a VM snapshot without reseeding.
    • Hand-rolled ECDSA with an RNG k, or a custom RNG callback.
  • Design defense
    • Long-term keys from getrandom(2), arc4random_buf, OpenSSL RAND_bytes (checked).
    • RFC 6979 (deterministic ECDSA) and Ed25519 (RFC 8032 section 5.1.6; OpenSSL EVP_DigestSign with an Ed25519 key) remove the RNG from signing.
      • Fault attacks on deterministic signing are a known caveat; hedged variants exist (uncertain).
    • Block key generation until the OS RNG is seeded; reseed after fork or snapshot.
  • Sources
    • Heninger et al. 2012; RFC 6979; RFC 8032; OpenSSL RAND_bytes(3).

Key reuse across purposes (KDF, integrity)

  • Root cause
    • One key serves two purposes or two protocols, so an oracle in one becomes an attack on the other. Security proofs assume independent keys, and NIST SP 800-57 says one key, one purpose.
    • RSA: textbook decryption c^d and signing m^d are the same operation, so a decryption oracle is a signing oracle.
      • With PKCS#1 v1.5, a Bleichenbacher oracle can forge signatures under the same key (Jager et al., CCS 2015).
    • DROWN (2016): one RSA key in SSLv2 and TLS let the SSLv2 oracle decrypt TLS sessions.
    • CBC-MAC under the CBC encryption key is forgeable: with a zero IV the last ciphertext block equals the tag, so an encryption oracle is a MAC oracle (textbook result; primary source uncertain).
    • One key for both directions or in test and production widens the blast radius and creates nonce collisions.
  • Known attacks:
    • EMV joint security (2012, EMV payment cards): one RSA key for signing and encryption enabled signature forgery (Degabriele et al., CT-RSA 2012).
    • TLS 1.3 and QUIC signature forgery (2015, TLS 1.3 drafts and QUIC): a PKCS#1 v1.5 decryption oracle on the same RSA key forged signatures (Jager, Schwenk, Somorovsky, CCS 2015).
    • DROWN (2016, SSLv2 and TLS sharing an RSA key): an SSLv2 Bleichenbacher oracle decrypted TLS sessions (Aviram et al., USENIX Security 2016; CVE-2016-0800).
    • IKE key reuse (2018, IPsec IKEv1 and IKEv2): one RSA key across modes let a Bleichenbacher oracle in one mode break the others (Felsch et al., USENIX Security 2018).
  • Spot in C code
    • The same key buffer passed to both an encryption call and HMAC() or a signing call.
    • One key loaded from one config field and used for several features.
    • The same RSA EVP_PKEY used for both OAEP decryption and signing.
    • HKDF (EVP_KDF HKDF) with the same info for different outputs.
  • Design defense
    • Derive one key per purpose and direction with HKDF-Expand and distinct info labels (RFC 5869; OpenSSL EVP_KDF-HKDF(7)), or generate independent keys.
    • Separate keys per environment, tenant and protocol version; track key purpose in metadata.
  • Sources
    • NIST SP 800-57 Part 1 Rev 5 section 5.2; Jager, Schwenk, Somorovsky, CCS 2015; DROWN, USENIX Security 2016.

Invalid curve and small subgroup (KEM/DH, confidentiality)

  • Root cause
    • Short Weierstrass addition and doubling use a but never b, so an off-curve point (x, y) lies on another curve y^2 = x^3 + ax + b' and the server computes there.
    • The attacker picks b' with a point Q of small prime order q; d * Q lies in a subgroup of size q, and any response that depends on the shared secret reveals d mod q.
      • Repeat for many small primes and combine residues with the CRT to get d; this needs a reused static key.
      • With x-only shared secrets each residue is known only up to sign; more queries resolve it.
    • Real case: Jager, Schwenk, Somorovsky (ESORICS 2015) recovered keys from TLS-ECDH implementations.
    • Finite-field DH has the same shape: a peer value of small order (1, p-1) or outside the prime-order subgroup leaks key bits; Logjam also showed weak shared groups.
  • Known attacks:
    • Lim-Lee small subgroup (1997, DH-based protocols): peer values in small subgroups leak the static key modulo small primes (Lim and Lee, CRYPTO 1997).
    • Invalid curve attack (2000, elliptic curve protocols): off-curve points move the computation to a weak curve (Biehl, Meyer, Muller, CRYPTO 2000).
    • TLS-ECDH invalid curve (2015, Java and other TLS-ECDH stacks): static ECDH keys were recovered from unvalidated points (Jager, Schwenk, Somorovsky, ESORICS 2015).
    • Measuring small subgroup attacks (2017, TLS, IPsec, SSH DH): many servers used non-safe groups without subgroup checks (Valenta et al., NDSS 2017).
    • Monero key image (2017, CryptoNote Ed25519): cofactor-8 key images allowed double spends (Monero disclosure, 2017 (uncertain)).
    • Bluetooth fixed coordinate (2018, Bluetooth pairing): only the x coordinate was authenticated and y was not validated (Biham and Neumann, SAC 2019; CVE-2018-5383).
  • Spot in C code
    • Hand-rolled ECC (bignum arithmetic) that parses (x, y) without an on-curve test.
    • OpenSSL: EC_POINT_set_affine_coordinates or EC_POINT_oct2point results used with no EC_POINT_is_on_curve, EC_KEY_check_key or EVP_PKEY_public_check.
      • Source: OpenSSL man pages; which calls check the curve equation differs by version (uncertain).
    • OpenSSL DH: peer value not checked with DH_check_pub_key or EVP_PKEY_public_check.
    • A reused static ECDH key answering many requests, instead of ephemeral keys.
    • X25519 via OpenSSL EVP_PKEY_derive with its return value ignored; OpenSSL fails the derive on an all-zero output (uncertain).
  • Design defense
    • Validate public keys: not the identity, coordinates in range, on the curve, correct order (NIST SP 800-56A Rev 3 section 5.6.2.3).
      • P-256 has cofactor 1, so on-curve implies correct order.
    • Prefer ephemeral keys, so leaked residues cannot be combined.
    • X25519: an x-only Montgomery ladder; every 32-byte input is on the curve or its secure twist, and clamping clears the low 3 bits (cofactor 8). RFC 7748 allows aborting on an all-zero output.
    • Compressed points cannot encode an off-curve point because decoding solves for y.
    • Finite-field DH: use RFC 7919 named groups and check the peer value is in range 1 < y < p-1.
    • Ed25519 verification: reject small-order keys and R; check what the library rejects (OpenSSL behavior uncertain).
  • Sources
    • SP 800-56A Rev 3 section 5.6.2.3; RFC 7748 sections 5, 6.1, 7; Jager et al. 2015.

Token and format

These attacks let the untrusted token pick the algorithm or key it is verified with. Defense: pin the algorithm and key per use in configuration and ignore header hints.

JWT algorithm confusion (signature, auth)

  • Root cause
    • The verifier takes the algorithm (or the key) from the untrusted token header.
    • alg: none: a verifier that honors it accepts an unsigned token.
    • Key confusion: the server holds an RSA public key and expects RS256; the attacker sets alg: HS256 and MACs the token with the public key bytes as the HMAC secret.
      • A verifier that follows alg accepts it (McLean, Auth0 blog, 2015).
    • Header-driven key lookup is a related attack: jku, x5u, jwk or a kid used in a file path or SQL query.
    • alg names signature or MAC algorithms, not ciphers.
  • Spot in C code
    • A hand-written or library verify path that reads alg from the parsed header and dispatches on it (strcmp(alg, "HS256")).
    • A public-key PEM loaded as a byte string and passed as an HMAC key.
    • libjwt: the expected algorithm not passed to the verifier, or jwt_get_alg not compared to it after decode (API differs by libjwt version; uncertain).
    • exp, aud and iss not validated; header kid interpolated into a query or path.
/* Stubs so the fence compiles; the app defines these. */
typedef struct { const unsigned char *bytes; size_t len; } jwt_key;
typedef struct { char alg[16]; } jwt_hdr;
int parse_header(const char *tok, jwt_hdr *h);
int hmac_verify(const char *tok, const unsigned char *k, size_t n);
int rsa_verify(const char *tok, const jwt_key *key);

int verify_token(const char *tok, const jwt_key *key) {
    jwt_hdr h;
    parse_header(tok, &h);
    /* Finding: algorithm chosen by the token. */
    if (strcmp(h.alg, "HS256") == 0)
        return hmac_verify(tok, key->bytes, key->len);
    return rsa_verify(tok, key);
}
  • Design defense
    • Pin one algorithm per key and ignore the header's choice (RFC 8725 sections 3.1 and 3.2); reject any token whose alg differs.
      • Keys come from configuration or an allowlisted JWKS, never from the token.
    • Validate exp, aud and iss (RFC 8725, section numbers uncertain).
    • Reject none unconditionally.
    • Use asymmetric signatures when verifiers must not mint tokens.
  • Sources
    • RFC 8725; McLean 2015; libjwt docs.
